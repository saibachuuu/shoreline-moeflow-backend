# 站点管理员身份管理权限

## 范围（2026-10-05）

用户单独授权先收紧站点管理员的授予／取消操作。通知系统仍停留在计划审查阶段，本修复不实现或部署通知功能。

| 操作 | 权限 |
| --- | --- |
| 设置／取消站点管理员 | 服务端当前 `ADMIN_EMAIL` 指定的账号，且必须仍为未封禁站点管理员 |
| 其他已有管理员功能 | 保持原有权限 |
| 未来发送站点通知 | 所有有效站点管理员，不区分来源；目前只记录计划，没有发送接口 |

## 后端

- `User.can_manage_site_admins()` 从当前 `ADMIN_EMAIL` 和数据库用户状态计算能力，不新增数据库字段／角色，不迁移历史数据。
- 邮箱比较沿用不区分大小写的账号语义，并去除配置两端空白；配置缺失、空值、类型无效或账号不匹配时拒绝。
- `PUT /v1/admin/admin-status` 先验证登录、封禁状态和专属能力，再解析目标用户和执行修改。
- 其他管理员即使自己构造 HTTP 请求、伪造 `can_manage_site_admins` 或邮箱字段，也不能授予／取消管理员。
- 原 `admin_can()` 和其他管理员端点不改变，避免把未来“发送系统通知”误限制为站长专属。
- 本人用户信息增加 `can_manage_site_admins` 布尔能力。其他人的公开资料不返回该能力，也不暴露配置邮箱。

## 前端

- 站长在“站点管理 → 用户列表”保留设置／取消管理员操作。
- 其他管理员隐藏这两个操作，保留用户列表、新建用户、重置密码等原有功能。
- 没有能力字段的旧后端响应默认不显示管理员变更操作；切换 token／账号或降权时清除缓存能力。
- 前端隐藏只改善交互，安全约束由后端负责。已打开页面的能力可能暂未刷新，但接口会按当前状态重新判断。

## 配置与兼容

- 不改变 `ADMIN_EMAIL`、默认管理员创建、`ADMIN_INITIAL_PASSWORD` 或 `manage.py migrate` 行为。
- `ADMIN_EMAIL` 变更并在后端进程生效后，新指定的现任管理员获得管理权；旧管理员仍保留原有普通管理员身份。
- 仅邮箱匹配但不是管理员的账号不能自我提权。初始化流程是否授予管理员，继续按已有规则执行。
- 原有站长自降权、修改账号邮箱的行为不额外禁止；这可能使管理入口暂时不可用，需按已有运维配置／初始化方式恢复。
- 无新增环境变量，无迁移或 MongoDB 索引变化，旧前端也会被新的后端权限检查约束。

## 明确保留的安全边界

“其他不变”意味着**没有同时限制普通管理员重置站长密码等既有高权限操作**。因此，这次只封住直接授予／取消管理员的入口，不建立完整的站长账号隔离，也不承诺抵御持有其他既有高权限能力的管理员间接接管账号。

如需保护站长密码、邮箱、验证码访问和会话等路径，应另列范围、复核相关接口并授权实施；不在本次悄悄改变其他管理员功能。

## 验证范围

- 站长授予／取消；普通管理员与普通成员直接调用拒绝；匿名／封禁拒绝。
- 环境配置空值、缺失、大小写、配置更换；降权／邮箱变化后旧 token 不能继续操作。
- 本人能力返回与他人资料隐私；伪造请求能力不起作用。
- 其他管理员读取设置、管理用户、创建用户和重置用户密码的既有行为不变。
- 前端能力默认拒绝、账号／token 切换清理、降权清理及管理操作显隐。

实际测试和部署结果以交付记录为准；本文件不代替完整通知系统的审查批准。
