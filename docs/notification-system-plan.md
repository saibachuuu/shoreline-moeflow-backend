## 1. 目标、状态与范围

### 1.1 目标

建设独立于可选模块的**核心通知服务与通知中心**，统一管理站内通知和邮件投递。保留系统、团队、项目、个人四类的数据与接口契约；首版系统／团队／项目提供通用手动发送和收件展示，个人仅保留底层接口，不接入具体事件或建设专属 UI。后续模块可调用核心接口，但核心不得依赖具体模块。

本文中的状态标记：

- **已确认**：用户已经明确提出的要求。
- **拟采用**：计划中的实现细节；是否已实现／验证，以实施记录为准，不等于已经上线。
- **待决策**：存在实质性身份或权限歧义，实施相应功能前必须确定。

### 1.2 已确认要求

| 编号 | 要求 |
| --- | --- |
| C01 | 通知系统属于核心功能，不作为 `modules` 模块安装。 |
| C02 | 首版渠道为站内通知和邮件通知；现有邮件能力应纳入统一体系。 |
| C03 | 系统通知仅面向注册用户，不建设访客通知 UI。 |
| C04 | 系统通知仅有效站点管理员可发送，不区分环境变量指定或手动授予；普通团队、项目通知默认仅创建者可发送。 |
| C05 | 团队创建者可允许团队管理员发送团队通知，也可设置项目通知默认权限是否包括项目管理员。 |
| C06 | 除迁入的校对稿既有发送逻辑外，系统／团队／项目通知首版仅做通用手动发送入口；移除专用“阶段完成”入口，不新增业务事件自动触发。 |
| C07 | 团队、项目通知支持全员、管理身份、工作人员资质／职位和指定成员筛选。 |
| C08 | 团队募集是团队内部为某个项目募集人员，不向团队外或全站群发招募。 |
| C09 | 外部人员记录跳过；不做用户私信。 |
| C10 | 个人通知首版仅做受信服务端可调用的底层接口，不做个人发送页面、私信、订阅功能或具体事件生产逻辑，留给后续模块接入。 |
| C11 | 桌面端入口在左下角用户元素上方；移动端入口仅出现在底栏的“团队”和“我”之间。 |
| C12 | 保留此前移动端右上角的主题快捷开关，以及“我”内的主题、CDN 设置。 |
| C13 | 通知内容包含标题、正文，提供基础 BBCode 与可访问项目的名片展示。 |
| C14 | 通知系统先审查计划再实施；实际改动在 `dev`，不得直接影响 `main`。 |
| C15 | 单独先行收紧站点管理员身份管理：仅 `ADMIN_EMAIL` 指定且仍为有效管理员的站长可授予／取消管理员，其他管理功能不变。 |
| C16 | 全站消息管理允许有效站点管理员查看所有普通通知，支持筛选和搜索，并可在二次确认后撤回；不能凭全站管理权替团队／项目发送消息。 |
| C17 | 全站消息管理处发送站点通知也必须支持接收方筛选、指定用户及发送前预览，不限于全体广播。 |
| C18 | 站点发送与全站管理入口放在 `/admin/` 下；团队发送入口放在 `/dashboard/teams/:teamID/setting/` 下；项目发送入口放在项目的 `projects/:projectID/setting/base` 基础设置页。 |

### 1.3 首版拟包含

- 收件箱、详情、未读数量、分类、归档、通知偏好。
- 系统／团队／项目通用手动发送器、收件人筛选／搜索／预览和发送确认；团队／项目发送权限由创建者控制。
- `/admin/notifications` 全站消息管理：跨范围查看所有普通通知、筛选、搜索和二次确认撤回；该页面只可新建站点通知，不可代发团队／项目消息。
- BBCode 编辑、预览、项目名片与逐接收者权限校验。
- 人工创建并确认的普通公告支持即时／定时投递、失效与撤回；定时不是自动产生业务通知的触发器。
- 持久化投递记录、异步邮件、重试、幂等及故障恢复。
- 校对稿业务邮件完整接入；三类账号安全邮件只整合底层投递能力并与普通通知隔离；既有运维错误邮件按 §9.5 单列边界。
- 邀请／申请提醒与通知入口的衔接，具体策略见 §10.5。
- 个人通知底层接口、未来模块调用契约及零模块运行验证；不因此在首版增加实际事件生产者。

### 1.4 明确不做

- Web Push、浏览器系统通知、短信、即时通信、私信、评论和回复。
- 任何范围的专用“阶段完成”按钮、声明记录、职位确认权限或阶段通知 API；不做项目／语言／文件／批次级阶段状态管理。
- 自动识别翻译完成、自动进入下一阶段、任务依赖图、人员逐一签收、完整工作流引擎。
- 团队／项目邀请、申请审批、成员变更、项目完成／重开、OCR／导出完成等事件自动生成新的通知或业务邮件。
- 团队外招募、全站关注流、订阅页面、自动订阅及订阅对象管理。
- 任意 HTML、附件上传、远程图片嵌入、任意 iframe、插件可执行通知内容。
- 对旧业务记录无差别回填通知、补发历史邮件。
- 借本功能重构既有迁移体系或改变现有项目完成／重开规则。

### 2.2 现有邮件清单与迁移分类（2026-10-06 只读盘点）

当前共发现 **5 类邮件、2 条实际 SMTP 发送路径**。以下“触发”表示代码受理发送操作，不表示当前部署已开启邮件或收件人已收到；本次未核查线上秘密配置、未实际发信。

| 邮件 | 当前触发场景与目标地址 | 现有入口 | 首版接入范围 |
| --- | --- | --- | --- |
| 确认安全邮箱 | 注册时请求验证码，或修改邮箱时验证新邮箱；发送至通过新邮箱校验的填写地址，需要人机验证码。 | `POST /v1/confirm-email-codes`；`app/apis/v_code.py::ConfirmEmailVCodeAPI` | 安全邮件；只统一底层投递，不生成普通通知。 |
| 重置安全邮箱 | 已登录用户修改邮箱时请求旧邮箱验证码；地址从当前账号绑定邮箱取得，不接受任意目标地址。 | `POST /v1/reset-email-codes`；`ResetEmailVCodeAPI` | 同上；不得错误改发到新邮箱。 |
| 重置密码 | 忘记密码时主动请求验证码；填写邮箱必须已注册，并通过人机验证码。 | `POST /v1/reset-password-codes`；`ResetPasswordVCodeAPI` | 同上；不能受普通通知退订控制。 |
| 校对稿修改反馈 | 有校对权限的用户手动寄送，有有效校对差异时发给项目活跃翻译成员，可抄送操作者；细节见 §9.2。 | `POST /v1/projects/<project_id>/targets/<target_id>/send-proofread-draft`；`app/apis/project.py::ProjectSendProofreadDraftAPI` | 唯一需要完整迁入的既有业务邮件，创建 `project / proofread_feedback` 站内通知并按偏好投递邮件。 |

### 2.3 现有发送路径、开关与结果语义

| 路径 | 当前条件／行为 | 接入时必须注意 |
| --- | --- | --- |
| 验证码 → `VCode.to_email` → `send_email` → `tasks.email_task` | `DEBUG` 或 `TESTING` 开启时只调用 `to_log`；否则渲染模板并交给 Celery。最终任务受 `ENABLE_USER_EMAIL` 控制。 | 当前调试日志包含验证码和邮箱，不能原样并入新观测系统；安全任务仍需隔离。 |
| 校对稿 → `send_email` → `tasks.email_task` | 同样受 `ENABLE_USER_EMAIL` 控制，需要正常的队列消费者和 SMTP；没有验证码路径的 `DEBUG/TESTING` 自动免发分支。 | 不能仅因在测试环境就认为不会发信；实际收件人必须受保护。 |
| 错误日志 → `SMTPSSLHandler.emit` | 直接同步 SMTP 发信，不经过 Celery，只由 `ENABLE_LOG_EMAIL` 控制；没有 `DEBUG/TESTING` 自动免发分支，也不受 `ENABLE_USER_EMAIL` 控制。 | 关闭用户邮件不等于关闭全部邮件；运维通道需独立验收。 |

- `send_email()` 当前只调用 `.delay()` 入队，不等待 SMTP 结果；`email_task` 对关闭开关或多种 SMTP 失败返回文本，并非已有可靠投递状态、自动重试与幂等体系。
- 校对稿 API 当前入队后即返回“校对稿已成功发送至翻译邮箱”，验证码 API 返回重发等待时间；这些响应均不能作为邮件已送达的证据。接入后按 §9.4 区分受理、跳过、失败及未知结果。
- 用户邮件当前共用 `tasks.email_task`，在工厂的通配路由下进入 `default` 队列；不能假设已有专属安全邮件优先队列及消费者。
- `.env.sample` 的默认开关和源码配置不能证明线上实际启用状态；实施前只核对必要配置，不在文档、命令输出或一般日志中披露凭据和真实邮箱。

### 2.4 未发现的旧邮件与非迁移事项

按当前应用、可选模块及前端调用入口搜索，未发现邀请、申请审批结果、成员变更、项目完成／重开、OCR／导出完成等面向用户的业务邮件发送逻辑；失败时可能产生错误日志邮件，但不是用户完成通知。注册、换绑邮箱、修改密码操作完成也没有额外结果邮件入口。

这些都不属于“旧邮件迁移”，首版不增加其自动通知逻辑。邀请／申请仅保留既有待办展示衔接，个人仅保留底层接口；后续新增事件需另列发送者、收件人、权限、隐私与去重规则并经审查。

## 3. 审查决策表

### 3.1 已确认的站点身份规则与先行修复

**R01 已确认（2026-10-05）：系统通知由所有有效站点管理员发送，不区分管理员来源。**

用户在知悉原有后台可以授予其他用户站点管理员身份后，明确要求将两个权限分开：

| 操作 | 允许身份 |
| --- | --- |
| 授予／取消站点管理员 | 只有当前服务端 `ADMIN_EMAIL` 指定且仍为未封禁站点管理员的账号（站长） |
| 发送站点通知 | 所有有效站点管理员，包括站长和站长手动授予的管理员 |
| 全站消息查看／筛选／搜索／二次确认撤回 | 同上；R02 新增通知管理能力，不授予代发团队／项目消息权限 |
| 其他已有站点管理功能 | 保持现状，不因“站长”区分一并收紧 |

实现边界：

- 原主分支的用户管理界面与 `PUT /v1/admin/admin-status` 确实支持添加／取消管理员，本次不是删除这个功能，而是收紧调用者资格。
- 站长资格由后端运行时配置及当前数据库账号状态计算，不新增角色字段或历史迁移；不能信任前端传入的邮箱、布尔权限或 JWT 中缓存的旧身份。
- 原有 `admin_can()` 语义保持不变，未来站点通知使用有效站点管理员判断，不错误复用“管理管理员”的站长专属检查。
- 前端只获得自身的 `can_manage_site_admins` 能力，不下发 `ADMIN_EMAIL` 配置。普通管理员不显示授予／取消操作，直接请求同样拒绝。
- 配置缺失／空值、账号不匹配、已经降权或封禁时，不授予管理员管理权。
- 修改 `ADMIN_EMAIL` 后特殊管理权随生效配置切换；旧账号仍可能保留普通管理员身份和站点通知发送权。
- 原管理员初始化行为不改，站长改邮箱或取消自身管理员身份的恢复仍由运维配置／初始化负责。
- **“其他不变”的安全边界**：原有重置用户密码等高权限能力继续保留，包括可能作用于站长账号；因此此修复不等于建立了完全隔离、不可被其他管理员间接接管的站长安全层。若需保护这些路径，应另行确认范围。

这项小修复可以先行实施；**完整通知系统仍需审查本文其余内容后明确批准执行**。

### 3.2 拟采用的设计决策

审查者可按编号修改；未修改且整体批准后才作为实施依据。

| 编号 | 拟采用方案 | 原因／边界 |
| --- | --- | --- |
| D01 | 团队的两个管理员发送开关默认关闭，修改后实时适用于团队及现有项目；首版无项目级覆盖。 | 简化权限解释，避免“默认”只影响新项目而产生隐含历史差异。 |

| D08 | 桌面端采用完整通知页面而非浮层；进入列表不自动已读，打开详情才已读。 | 长正文、名片和历史检索更容易使用。 |

| D14 | 批量发件向发送者及有权的全站管理者展示投递汇总，首版不提供“具体谁读过”的逐人跟踪 UI。 | 全站消息查看不是用户收件箱托管；名单预览不等于已读追踪。 |
| D15 | 全站管理查询与普通收件／发件查询使用独立授权入口；撤回逐条二次确认，拟要求理由、版本校验及审计。 | 落实 C16，跨范围查看不变成代发、改写或冒充收件人权限；确认不能代替后端鉴权。 |
| D16 | 站点收件筛选首版拟支持全体有效用户、站点身份、团队／项目有效成员范围及手选用户；查询与预览均服务端分页。 | 落实 C17；即使按团队／项目筛选接收方，发出的仍是站点通知，不是代表该团队／项目发言。 |

### 3.3 已确认的全站消息管理边界

**R02 已确认（本次补充）：有效站点管理员可以查看、筛选、搜索全站所有普通通知，并可在二次确认后撤回，但不能凭这项管理权代发团队或项目通知。发送站点通知时也支持接收方筛选。**

- 此处“所有消息”指核心通知系统已保存的普通通知，跨发送者、团队、项目与通知分类，包含校对反馈；未来个人底层接口产生的普通通知也遵循相同管理规则，不因此在首版增加个人事件生产者。
- 不将此范围限缩为“只有站点公告”或“仅管理员本人收到／发出的消息”；管理员即使不是相关团队／项目成员，也可经专用管理入口查看消息标题、正文和投递汇总。
- 安全验证码／重置邮件和独立运维日志不属于普通通知，继续隔离；旧 `Message` 历史数据的只读兼容／迁移仍按 §15.2 另行审查，不暗中回填。
- 管理页面只提供站点通知新建入口，不能修改团队／项目消息的发送者、正文、接收人或类别，也不能通过复制、重新发布、人工补发邮件等方式代发。
- 若站点管理员同时是某团队／项目的合法创建者或获准管理员，仍可按该范围的普通规则在对应设置页发送；这来自其独立范围身份，不来自全站管理权。
- 全站查看／撤回与站长专属的“授予／取消管理员”仍是不同权限；站点管理员来源不影响通知管理资格，降权／封禁后立即失效。

## 4. 分类与发送权限

### 4.1 分类不是来源

- `category`：`system`、`team`、`project`、`personal`，用于底层分类与查询；`personal` 首版仅保留接口能力，前端启用范围见 §10.3。
- `source`：核心或模块的稳定来源标识，用于审计和展示。
- `event_type`：首版实际业务入口仅使用通用手动公告 `announcement` 与迁入的 `proofread_feedback`；个人底层接口为未来模块预留命名空间事件标识，不内置具体生产者。
- 分类、来源、渠道分别建模。模块产生的内容不应全部挤进一个“模块”分类。
- 核心允许未来模块调用，但不提供匿名或任意前端用户都能指定接收者的通用群发接口。

### 4.2 权限矩阵

| 行为 | 系统 | 团队 | 项目 |
| --- | --- | --- | --- |
| 普通公告发送 | 所有有效站点管理员（R01 已确认） | 创建者；开关开启后管理员 | 创建者；开关开启后实际项目管理员 |
| 修改管理员发送开关 | 不适用 | 仅团队创建者 | 由所属团队创建者在团队设置中控制 |
| 校对稿既有业务入口 | 不适用 | 不适用 | 沿用 `PROOFREAD_TRA` 等现有校对权限校验，不等同于普通公告发送权限 |
| 发件预览／查询可选成员 | 同发送权限 | 同发送权限，限当前团队 | 普通公告同发送权限；校对稿收件人由既有业务规则限定 |
| 范围内普通撤回 | 原发送者且当前仍有权限，或对应范围创建者 | 同左 | 同左；不撤销翻译／校对修改或项目业务状态 |
| 全站管理查看／搜索／筛选 | 有效站点管理员，查看所有发送者的消息 | 同左，无须成为团队成员 | 同左，无须成为项目成员 |
| 全站管理撤回 | 有效站点管理员，须二次确认及审计 | 同左，不获得团队代发权 | 同左，不获得项目代发权 |
| 查看收件箱 | 仅自己的收件记录 | 同左，并检查范围资格 | 同左，并检查范围资格 |

新权限代码名称在实现时确定。**不能只把 `SEND_NOTIFICATION` 加入已有宽泛管理员权限集合**：现有团队管理身份会继承项目权限，必须经过通知专用策略判断。全站 `view/search/revoke` 能力也不能隐式包含团队／项目的 `publish/edit/resend`；个人普通通知的全站查看／撤回遵循 R02，但仍无个人发送 UI。

管理策略更新使用期望版本进行并发检查，记录操作者、旧值、新值、作用范围。管理员即使拥有普通团队设置编辑权限，也不得修改这两个创建者专属开关。直接构造 API 请求必须得到同样的拒绝。

预览、提交、定时到期及实际分发阶段分别进行相应权限检查。权限被收回时不能凭旧页面或旧预览 token 继续群发。

### 4.3 全站管理与普通用户查询隔离

- 管理员通过专用 `/v1/admin/notifications` 查询访问所有普通通知；普通 `/v1/me/notifications` 仍只返回本人收件，普通发件管理仍检查范围权限，不能给这些接口加一个客户端可控的“管理员查看全部”开关。
- 全站查询和详情每次都检查当前有效站点管理员身份；不要求管理员在消息收件名单中，也不要求其具有原团队／项目成员身份。筛选、结果数量、搜索片段与正文使用同一管理权限，避免只保护详情而泄漏列表。
- 查看管理详情不产生收件记录，不标记任何人的已读／归档，也不修改管理员自己可能已有的收件状态；管理页与个人通知中心是两套查询语义。
- 管理员有权查看的是通知本身及安全的管理上下文，不据此获得关联项目文件、图片、译文编辑或其他业务资源的额外权限。正文与历史内容可按 R02 展示；动态项目名片／资源跳转仍按 §7.4 校验。
- 禁止通过管理入口编辑或代发团队／项目消息、调整接收名单、恢复已被管理撤回的消息或触发人工重新寄送；仅允许受审查的查看与撤回能力，以及独立的站点通知创建。
- 管理视图缓存与普通收件缓存隔离；退出、身份切换或降权时清理缓存，服务端不继续返回跨范围内容。管理搜索／详情访问和撤回均记录必要受限审计，见 §12.7。

## 5. 收件人选择与权限变化

### 5.1 范围定义

- **系统**：有效的注册账户；跳过已删除、封禁账户。不要求有邮箱才能收到站内通知；支持全体、条件筛选或手选用户，具体见 §5.5，不默认只能广播全站。
- **团队**：当前团队有效注册成员。管理人员包含创建者／管理员；普通成员是非这两类的有效成员。资质按 `worker_qualifications` 筛选。
- **项目**：当前项目实际有效注册成员；按项目标签筛选。只有团队访问继承而没有实际项目成员记录的人，不默认属于“项目全员”。
- `invited` 不是正式接收成员；`removed`、未注册外部人员不计入接收者。
- 允许发送者在所选范围内收到一份自己的通知；不自动额外抄送，校对稿现有“抄送自己”单独保留。
- 不存在资格匹配者时禁止发布空通知，提示调整筛选或分配人员；不自动找管理员补发。

### 5.2 筛选语义

```text
condition 模式：
  有效范围用户／成员
  ∩ 基础身份条件（条件内 OR）
  ∩ 资质／职位条件（条件内 OR）

manual 模式：
  手选 user_ids ∩ 有效范围用户／成员
```

- “全员”不与其他筛选条件同时提交，防止 UI 与后端解释不一致。
- 手选模式不得携带范围外账户；后端拒绝非法选择，而不是扩展权限。提交后失效的原有效成员可从实际发送名单中剔除并报告数量。
- 预览返回可发送人数、分页名单、外部／失效成员剔除提示。查询和人数本身也受权限控制。
- 前端不下载全站用户列表再自行筛选。团队／项目发送的成员搜索必须限定当前范围；站点发送可由有效站点管理员执行全站候选用户查询，但必须服务端筛选、分页、限流并隐藏非必要邮箱信息。

### 5.3 快照与时点

- 即时发送：后端重新解析并持久化接收名单。**持久化名单完成**后称为收件人快照；不宣称跨 MongoDB 多批查询获得了原子的历史成员快照。
- 定时发送：保存筛选规则，页面明确提示“人数在实际发送时重新计算”；到期检查发送权限后生成名单，不使用过时预览直接投递。
- 名单固化后，重试不得把后来加入的成员不断追加进同一通知。
- 实际投递时再剔除已失效资格的接收者；剔除只能缩小名单，不能扩大。
- 后来注册／加入者不补发旧通知。未来如需要有效公告墙，应与个人收件箱分开设计。

### 5.4 权限失效后的读取

- 本节适用于普通收件箱／详情。读取团队／项目通知须同时验证收件人归属和当前范围资格，不仅校验收件记录中的 user_id；R02 专用全站管理视图按 §4.3 独立授权，不复用这些成员资格限制。
- 已退出团队、被移出项目、源项目删除时，不继续返回标题、正文、摘要、封面、原始 BBCode 或搜索片段。
- 可以保留一个不含敏感信息的“关联通知已不可访问”占位，默认不计入未读数；列表与未读统计使用同一可见性规则。
- 撤回、过期、失去权限均不能收回用户以前已经看见、截图或收到的邮件；UI 不做此类承诺。
- 发送者手工写入正文的信息无法通过卡片权限机制自动脱敏；发送预览需要提示“正文对选定接收者可见，站点管理员可通过全站管理查看并撤回通知”，不能将内部通知宣传为对站点管理者不可见。

### 5.5 站点通知接收方筛选

站点发送与团队／项目发送一样必须有收件人选择及预览，不允许“点击发送即默认全站群发”。拟采用以下首版选项：

| 模式 | 可选条件 | 规则 |
| --- | --- | --- |
| 全体 | 全部有效注册用户 | 操作者明确选中“全体”，显示人数并确认；不能同时提交其他条件。 |
| 条件 | 站点身份：全部／有效站点管理员／非站点管理员 | 同一字段多个值取并集，与其他筛选字段取交集；“非管理员”不等于团队普通成员。 |
| 条件 | 指定团队的有效注册成员，或指定项目的实际有效注册成员 | 团队选择与项目选择作为两种范围模式，首版不混用；同一模式多个范围取并集，与站点身份条件取交集。外部、邀请中、移除成员不因筛选被纳入。 |
| 手选 | 搜索并选择指定注册用户 | 按用户 ID、用户名／别名查找，分页返回；与条件模式互斥，后端重新校验有效性并去重。 |

- 站点通知允许仅发给筛选出的部分用户，仍为 `category=system`，由真实站点管理员署名；按团队／项目选择接收方只是选人，不获得团队／项目发送权限，不伪造范围消息或创建者身份。
- UI 的“已有消息列表筛选”与“新站点通知收件人筛选”完全分开；不能把搜索结果、消息作者或现有消息的收件名单自动带入新通知，必须明确选择并确认。
- 预览展示筛选摘要、去重后的站内人数、预计邮件人数、分页候选名单及无邮箱／偏好关闭等跳过提示；可搜索候选用户而不返回全量账号、完整邮箱列表或他人的已读记录。
- `all`／`condition`／`manual` 模式及请求字段在 P0 固化；不能接受任意数据库表达式、前端传入邮箱或自由正则绕过校验。
- 提交、定时到期、实际投递按 §5.3 重新检查管理员身份与选人资格；名单封存后重试不增加新用户，空名单拒绝。邮件继续遵守接收者的系统分类偏好，不设置强制邮件开关。

## 6. 手动发送入口与首版业务边界

### 6.1 入口清单

| 分类／业务 | 首版入口 | 边界 |
| --- | --- | --- |
| 系统（站点） | `/admin/notifications` 的“发送站点通知”，发送页拟为 `/admin/notifications/new` | 有效站点管理员筛选接收方后发送；全站管理可看所有普通通知，但此处只能新建站点消息。 |
| 团队 | `/dashboard/teams/:teamID/setting/` 下的“通知管理”，子路由拟为 `notifications` | 按创建者控制的发送权限，手选成员或使用受限筛选；团队内招募也用此入口。 |
| 项目 | 项目 `projects/:projectID/setting/base` 基础设置页中的“项目通知”区块 | 提供发送与发送记录入口，沿用当前项目路由前缀；按普通项目公告权限发送，无阶段／交接按钮。 |
| 校对稿反馈 | 原“寄送校对稿”业务入口 | 沿用现有校对权限、差异内容与收件规则，只将内部投递改接通知服务，详见 §9.2。 |
| 个人 | 受信服务端底层接口 | 无首版个人发送器、公开 HTTP 发送接口、专属页面、订阅或具体事件生产者。 |

账号安全邮件与运维错误邮件按 §9.3、§9.5 保留独立流程，不因上述手动通知范围而停用或强制人工介入。

通知中心仍是个人收件入口 `/dashboard/notifications`，不混入全站管理功能。团队采用设置子标签，项目基础页放入口而不是把长篇发送表单嵌入基础设置；编辑器与列表可进入同范围子页。`/dashboard/projects/:projectID/setting/base` 是直接项目入口示例，实际导航复用匹配到的项目路由前缀。页面可访问不代表拥有通知发送权限，前后端均单独校验。

### 6.2 通用手动发送流程

1. 有权限的操作者从站点／团队／项目对应入口打开发送器，后端核验当前身份与范围。
2. 人工填写标题、正文，按需插入可访问项目的名片；事件类型由服务端固定为 `announcement`，不能伪装成校对业务或受信模块事件。
3. 手选接收成员或配置 §5 的筛选条件；没有有效收件人时不发布。
4. 预览内容与收件人，选择是否请求邮件；默认不勾选邮件，并提示接收者偏好及权限变化可能使邮件跳过。
5. 操作者确认即时发送，或明确设置定时投递时间；提交带幂等键的人工发布请求。
6. 返回“已受理／投递中”，允许查询站内分发和邮件汇总；不将 SMTP 受理伪称为所有人已收信。

保留原方案的人工定时选项：定时只延后执行已由操作者创建并确认的发布意图，不扫描业务状态来自动生成公告；到期仍须重查权限。自动分块、队列重试及故障恢复也不属于新增通知触发器。

### 6.3 不产生工作流副作用

- 首版不定义阶段声明、阶段状态、确认人字段或专用阶段 API，也不按职位推荐固定的下一阶段流程。
- 发出、读过、归档或撤回通知均不改变 `ProjectStatus`、翻译／校对内容、人员分工或编辑锁定；现有完成／清空／重开行为不变。
- 进度达到 100%、上传／删除文件、邀请或申请处理、成员变化、OCR／导出完成等操作不自动创建新的普通通知；安全邮件和独立运维告警不属于这一普通业务触发范围。
- 普通公告在各项目状态下是否可发送仅依照独立通知权限，不顺带改变现有生命周期权限；校对稿继续执行其既有业务校验。
- 用户可以在普通正文中自行描述工作进展，但系统不将该文本视作经过验证的完成声明，也不据此更新业务状态。

### 6.4 重复、再次发送与更正

- 同一次提交的双击或网络重试复用幂等键，不重复创建通知。
- 有权限的操作者明确再次发送时使用新操作 ID；不能因内容相同永久禁止再次公告或再次寄送校对稿。
- 已发布内容不可原地修改；更正通过新的手动通知表达，并可关联前一次记录。
- 撤回只影响通知展示和未执行投递，不能回收已寄出的邮件，也不撤销任何业务操作；全站管理撤回的二次确认与审计按 §8.4。

## 7. 通知内容、BBCode 与项目名片

### 7.1 内容与约束草案

| 项目 | 拟定首版限制 |
| --- | --- |
| 标题 | 纯文本，1–200 字符 |
| 正文 | 最多 10,000 字符，限制解析节点数和嵌套深度 |
| 格式 | BBCode v1，纯文本通知视为其子集 |
| 单条项目名片 | 最多 5 个不同项目，重复引用可复用解析结果 |
| 附件／远程图片 | 首版不支持 |
| 语言 | UI 文案进入现有国际化机制；用户正文保持原文，不自动翻译 |

以上是审查默认值，应以实际移动排版和性能测试校正，不因前端限制而省略后端限制。

### 7.2 BBCode v1

支持：`[b]`、`[i]`、`[u]`、`[s]`、`[quote]`、`[list]`／`[*]`、`[url=...]`、`[project]...[/project]`。

```text
[b]《示例项目》募集校对人员[/b]

[project]本站项目ID或完整项目链接[/project]

[list]
[*]募集职位：校对
[*]工作范围：简体中文
[/list]

[quote]有意参与的团队成员请联系项目负责人。[/quote]
```

- 不支持任意 HTML、脚本、样式、远程嵌入、事件处理器和自动执行。
- 链接只允许明确的安全协议（首版 `https`／`http`）；拒绝 `javascript:`、`data:`、`file:` 等。
- 优先评估复用现有 `src/utils/bbcode.tsx` 的解析与安全 URL 能力，以通知专属选项／白名单补齐列表、引用、项目标签和复杂度限制；不改变其他页面原有标签策略。采用结构化解析，不以简单正则替换后直接拼接 HTML。前端使用 React 节点渲染，邮件使用受控模板并转义。
- 未知标签按普通文本显示；无法安全恢复的嵌套、超深、超长内容给出校验错误，防止解析耗时攻击。
- BBCode 保存格式版本；前后端共用测试样例，确保预览、详情、邮件降级语义一致。

### 7.3 编辑与项目插入

- 提供基础工具栏及预览，不要求用户记忆 BBCode。
- “插入项目”在用户当前可访问的项目内搜索；选中后保存稳定项目 ID，而非固化封面签名 URL。
- 粘贴**独立的本站项目链接**时给出转换名片提示；普通行文内链接不强制变成大卡片。
- 仅识别配置允许的本站源与已知项目路由，CDN／备用网址由通用站点配置归一化，不硬编码当前开发域名。
- 不请求用户粘贴的任意服务器来抓取标题／封面，避免 SSRF、开放重定向和信息泄漏。

### 7.4 项目名片权限

1. 插入／发布时，发送者须有项目访问权限；不能通过猜测 ID 获取项目名称。
2. 阅读时，以**接收者当前身份**批量解析项目元数据；不能把发送者的预览结果缓存后发给所有人。
3. 无权访问、项目删除、权限查询失败时，统一降级为“关联项目不可访问”，不区分错误原因泄漏存在性。
4. 降级时响应中也不得携带名称、封面、团队名、目标语言等隐藏数据，不仅是 CSS 隐藏。
5. 名片本身不授予加入或访问权限；团队招募依旧使用现有申请／邀请流程。
6. 缓存必须按接收者及权限变化隔离；不能共享包含私有元数据的 HTML。封面沿用现有受控 URL 获取机制。
7. 前端身份切换、退出登录时清除通知和名片缓存。
8. 全站管理详情可按 R02 查看通知原有标题／正文，但动态名片及资源链接以管理员自己的当前业务访问权限解析，不借通知查看权额外读取项目资源；管理缓存不可用于普通收件详情。

### 7.5 邮件降级

- 普通通知邮件优先展示通用通知类别、发送时间、简短提示和站内详情链接；默认不复制私有团队／项目的完整正文与自定义标题。
- 系统公告可渲染经转义的正文；私有业务正文完整邮件展示若需要，应作为额外披露策略审查。
- 项目名片在邮件中降级为不泄露名称／封面的“登录后查看关联项目”链接。
- 邮件同时生成 HTML 和纯文本版本，外链及换行有明确回退。
- **校对稿反馈是既有例外**：保留现有详细差异正文，明确其一旦发送就无法撤回；不得用普通通知隐私降级悄悄删除原有业务内容。

## 8. 通知生命周期

### 8.1 发布状态

拟采用：`draft` → `scheduled` 或 `preparing` → `dispatching` → `published`。

- `draft`：可编辑、预览，不生成收件记录或邮件。
- `scheduled`：可在执行前修改／取消；到期重新检查发送权限和收件人。
- `preparing`：请求已可靠保存，正在解析／固化名单；还未对接收者公开。
- `dispatching`：名单已封存，分批生成收件和投递记录；可能部分完成。
- `published`：站内分发完成，邮件可能仍在独立重试；不能把此状态解释成全渠道成功。
- `cancelled`／`failed`：未发布或未能继续发布，原因可供有权限的发送者查看。
- `revoked_at`、`expires_at` 为独立可见性字段，避免用一个状态混合发布、过期和邮件成败。

校对稿沿用现有即时操作，不新增业务草稿／定时寄送入口；普通公告的定时必须源于明确的人工发布请求，不承诺离线发送。

### 8.2 时间与定时

- API 使用带时区的 ISO 8601，服务端统一存 UTC，前端按用户／浏览器时区展示，并在定时确认处显示明确时区。
- 校验 `expires_at > publish_at`，过期通知不继续扩散，不计入普通未读角标；历史可以显示失效标记。
- 维护公告需提前发送；系统关停后，本站无法继续接收请求或投递新邮件，不能宣传为停机期间的独立告警系统。
- 定时任务因停机迟到时先检查过期时间；超过拟定最大迟到窗口 1 小时的公告标记待处理，不盲目在维护结束后大量补发。
- 启用定时必须一并部署可靠的周期扫描，不以浏览器在线或有人访问网站为触发条件。

### 8.3 撤回与归档

- 撤回操作记录操作者、时间和理由，普通收件视图隐藏原内容或显示撤回占位；专用全站管理视图仍可按 R02 查看原通知与撤回记录，不能以撤回删除审计证据。
- 尚未发送的邮件尽力取消；已经被 SMTP 接受、正在发送的邮件无法保证撤回，操作页面明确提示。
- 用户归档只修改自己的收件箱，不删除其他人的通知或发送审计。拟定“归档并标记已读”，不让隐藏归档项持续占用角标。
- 首版没有用户硬删除全局事件接口，没有批量清空后台审计功能。

### 8.4 全站管理撤回与二次确认

- 有效站点管理员可撤回任何发送者的普通通知，包括团队、项目、校对反馈及未来个人事件；不要求其属于原范围。拟覆盖已发布／分发中通知的撤回，以及定时／准备中发布意图的取消；草稿未发生投递，管理取消时同样保留记录。
- 操作必须逐条二次确认，首版不做批量一键撤回。第一步点击“撤回／取消投递”，第二步在确认对话框核对消息 ID、标题、类型、发送者、所属范围、当前状态与影响汇总，再明确提交；关闭弹窗不产生写操作。
- **拟定保护措施**：理由必填并限制长度；请求携带显式确认、期望版本和幂等键。服务端再次校验当前管理员身份、目标和版本；缺少确认、已降权或版本变化时拒绝执行，要求刷新后重新核对。
- 二次确认降低误操作，但不替代后端授权、限流和审计，也不能证明获授权管理员绝不会滥用。审计记录管理者、原发送者、通知 ID、范围、时间、理由、前后状态及执行结果，不复制整篇正文。
- 使用原子状态／版本条件落下管理撤回，分发和邮件 worker 发送前重查全局撤回／取消状态；并发发布、重试或原发送者编辑不能使被撤回记录恢复投递。重复确认返回已有结果，不重复创建撤回动作。
- 撤回后普通收件详情及搜索隐藏正文，未读统计一致；全站管理保留原内容和撤回原因。不能修改原发送人、消息内容或收件人，不能删除记录、替用户标记已读或改变项目业务状态。
- 确认框和结果页都提示：已被 SMTP 接受或正在发送的邮件无法保证收回，用户已看到的内容也无法抹除；未投递部分尽力取消并报告真实结果。

## 9. 站内与邮件渠道

### 9.1 普通通知渠道选择

```text
站内投递 = 有效收件资格
普通邮件投递 = 发送者选择邮件
             AND 接收者对应分类允许邮件
             AND 有有效的已验证邮箱
             AND 实际发送时仍有接收资格
             AND 未撤回／未过期
```

- 业务邮件不接受前端传任意 `to_address` 绕过用户收件资格。
- 无邮箱、未验证邮箱、关闭邮件偏好时，站内照常发送；记录邮件跳过原因，不当作投递故障无限重试。
- 账号安全邮件发送到验证流程规定的目标地址，不受“必须已验证”规则阻断。
- 邮箱地址在真正投递时从当前账号解析，并核对有效性；不向已被用户解除绑定的旧邮箱重试业务邮件。
- 普通邮件偏好关闭后，仍未投递的业务邮件要重新检查并跳过。
- 当前账号模型没有独立 `email_verified` 字段；“已验证邮箱”的历史账号判定须在 P0 按 §9.6 固化，不能假设现有数据库已经具备该字段。

### 9.2 现有校对稿反馈接入

**当前行为与兼容基线（隐私及结果语义按下述方案收紧）：**

- 入口为 `ProjectSendProofreadDraftAPI`，必须登录并通过 `PROOFREAD_TRA` 校对权限检查；目标语言必须属于当前项目。
- 仅在用户手动寄送时计算内容；后端支持可选 `file_id` 限制单个有效图片文件，否则扫描项目全部有效图片。当前翻译器调用传项目与目标语言，不传文件范围。
- 使用所选目标语言的译文／校对稿；至少有一处校对内容去除首尾空白后非空且不同于原译才可寄送，无变化时返回 `ProofreadDraftNoChangesError`。不会因保存校对内容自动发送。
- 收件人取项目 `status="active"`、`tags="translator"`、绑定注册用户且有邮箱的成员，按规范化邮箱去重；**当前未按目标语言进一步筛选翻译成员**，也不能擅自改成只发给具体译文作者。
- `cc_myself` 默认开启；操作者已在翻译收件人中时不重复。没有翻译收件人但开启抄送且操作者有邮箱时，仍允许只发送给自己；否则返回 `NoTranslatorMemberError`。
- HTML／纯文本邮件保留修改页面、原译／校对内容、差异展示、图片链接与项目入口。正文及 `Reply-To` 披露操作者回复邮箱；当前共享 `To/Cc` 头还会披露其他收件人邮箱，这不是新的逐人投递方案应继续复制的行为。

**拟接入方式：**

- 保留 `send-proofread-draft` 路径、参数、用户操作、权限、语言／文件范围、无变更提示与差异内容；只替换内部主投递路径，不能同时调用旧发送器和新 outbox。
- 收件人沿用上述职位／成员业务规则，先构造有效注册用户的站内名单，再做邮件地址校验；不能仅从旧邮箱列表反查用户，也不能因无邮箱而剔除有效站内收件人。外部、邀请中、已移除、封禁或已删除账号不新增投递。普通项目公告发送开关不阻断原有校对功能。
- 按一次明确操作创建 `project / proofread_feedback` 通知与对应站内收件记录；保留“无翻译时仅给自己”的既有情况，不用普通公告的收件筛选器扩大业务范围。
- 默认请求邮件，符合“寄送校对稿”语义；但遵守普通项目邮件偏好。无邮箱或偏好关闭时站内仍可送达，并展示邮件跳过原因；全部跳过时不能显示“邮件已寄送”。
- 各接收者独立投递，不在 `To/Cc` 头公开其他用户邮箱。“抄送自己”作为操作者的一份独立投递，与其翻译成员身份及其他重复身份去重。
- 发送预览清晰提示详细差异、图片链接和操作者回复邮箱的既有披露；保留 §7.5 的详细邮件例外，不自动公开更多个人信息。
- 同一次操作重试复用幂等键；再次明确点击寄送可形成新操作，不能把“存在相同差异”当作永久去重条件。

### 9.3 安全邮件隔离

- 邮箱确认、修改邮箱、密码重置：按 §2.2 三类入口继续由安全流程决定接收目标、验证码有效期及重发频率，不新增通知发送 UI，也不改变验证完成后的账号操作。
- 注册用户尚不存在或新邮箱尚未验证是正常安全流程；不得套用普通通知的“已注册收件人／已验证邮箱”限制阻断。换绑时旧邮箱验证、新邮箱确认不得混用。
- 三类安全邮件不生成普通通知事件或站内收件记录；验证码／重置链接不得进入可检索业务日志。
- 共用邮件传输、错误分类与可观测性，但使用独立业务类型和优先处理路径；批量公告不得挤占密码重置处理能力。
- 重试前检查验证码是否仍有效，过期、已使用或已被新验证码替换则停止；不重复寄送已经失效的秘密。
- 只持久化必要关联 ID／状态；敏感载荷不能出现在管理员通知详情、错误堆栈、调试输出或普通队列诊断截图。
- 如果底层邮件任务必须短期携带敏感载荷，应限制消息保存和结果记录，保证日志脱敏，不复制到普通通知 outbox。
- 迁移时明确处理现有 `VCode.to_log` 明文验证码日志；开发测试改用受控测试设施，不把秘密复制进统一日志或管理员通知详情。

### 9.4 邮件状态

建议：`pending`、`leased`、`accepted`、`retry_wait`、`skipped`、`failed`、`unknown`、`cancelled`。

- `accepted` 只表示 SMTP 服务接受，不表示到达收件箱或用户已阅读。
- SMTP 拒绝、连接前失败、接收后超时应区分。最后一类可能已经发出，标记 `unknown`，不承诺自动重试绝无重复。
- 用户邮件未配置或 `ENABLE_USER_EMAIL` 关闭时，明确显示未投递／渠道不可用，不伪报成功；运维邮件使用独立开关，不套用此条件。
- 替换当前“入队即成功”的用户提示：HTTP 受理、Celery 入队、SMTP 接受与收件箱送达是不同状态；兼容原路径不等于保留误导性的成功语义。
- 密码、验证码、SMTP 凭据、完整邮箱列表不进入发件汇总日志。

### 9.5 运维错误邮件边界（拟采用）

- `ENABLE_LOG_EMAIL` 控制的错误日志邮件单列为运维告警，不等同于站点管理员手动发布的 `system` 通知。首版保留独立能力，不把错误记录自动写入普通 `Notification`、收件箱或普通业务 outbox。
- 收件人限定为明确配置的运维地址，不改成全体管理员／用户；完整日志与堆栈只在受限运维渠道流转，普通通知页面不可搜索或查看。
- 可复用 SMTP 配置读取、错误分类与脱敏观测，但不要求必须经过通知服务、MongoDB 或同一 Celery 队列才能告警；改造前验证业务队列不可用时的独立告警路径。
- 告警发送失败不得再经同一邮件日志处理器递归告警；限流、重复错误合并与故障记录的具体方式在 P0 固化，不能借整合放大邮件风暴。
- 保留独立开关与开发收件保护；关闭普通通知或用户邮件不能被误认为运维邮件也已关闭。
- 是否增加仅运维可见的站内告警中心属于后续独立需求，本首版不建设。不能把本站通知中心宣传为站点停机时仍可工作的独立监控系统。

### 9.6 接入前必须确认的现有问题

1. **错误／回复邮箱配置读取。** `app/config.py` 当前将 `EMAIL_ERROR_ADDRESS` 与 `EMAIL_REPLY_ADDRESS` 都赋为 `env.get("EMAIL_ADDRESS", "")`，并未读取各自同名环境变量。错误邮件因此可能发给发件地址；校对稿显式传入的回复地址另行生效。实施前核对并确认期望目标、兼容回退及测试用例，不能在未确认真实收件人时静默改配置后发信。本次仅记录问题，不修改配置代码。
2. **已验证邮箱的判定。** `User.email` 当前为必填唯一字段，没有独立验证标志；正常注册与换绑依赖验证码校验，但不能直接推断所有历史／初始化账号的验证状态。P0 必须确定可证实的判定规则与异常处理，不直接增加必填字段、把所有旧账号视为未验证或未经依据全部放行；需要历史数据改写时按 §15 单独审查。
3. **投递成功与敏感日志。** 当前 SMTP 错误返回文本、入队后成功提示和验证码明文日志须分别纳入状态适配与脱敏验收，不能当作统一发送能力已经具备可靠性。
4. **开发发信保护。** 验证码的 `DEBUG/TESTING` 分支不能保护校对稿和错误日志邮件。迁移测试须覆盖两条 SMTP 路径、两个独立开关及收件白名单／测试 SMTP，禁止仅凭环境名称推断安全。

## 10. 前端交互

### 10.1 桌面端

- 通知入口固定在侧栏底部用户元素上方，位于可滚动团队列表之外。
- 展开显示图标、文字、未读角标；折叠显示图标、角标和键盘可访问的提示。
- 点击进入 `/dashboard/notifications`，不使用容易被长内容挤压的弹出浮层。
- 不修改现有桌面主题、CDN 模块设置和用户菜单行为。

### 10.2 移动端

底栏顺序固定为：**项目｜团队｜通知｜我**。

- 通知入口仅由现有底栏承载，不向项目预览、翻译器等无底栏页面额外插入铃铛。
- 通知首页加入移动 Tab 页识别，使进入通知首页后底栏继续存在。
- 通知详情、发送页采用普通二级页：返回按钮，按现有规则不显示底栏；保留这些页面原有的右上角主题快捷开关。
- “我”内现有主题和 CDN 设置不移动、不删除。
- 考虑 iOS 安全区、软键盘和窄屏；项目原有两列缩略图与响应式工具栏不回退。

### 10.3 收件箱与详情

- 首版启用“全部／系统／团队／项目”收件分类；`personal` 仅保留通用数据与底层接口支持，不建设个人专属页面、入口或订阅 UI。未来模块接入后的展示另行启用，不在首版伪造个人通知数据。
- 未读筛选、按最新发布时间排序、游标分页、逐条标记已读／未读、全部已读、归档及已归档列表。
- 进入列表不自动已读；详情成功加载后才提交已读。不可访问或加载失败不执行误导性成功动作。
- 全部已读以请求时的截止位置为界，不把并发刚到达的新通知一并清空。按钮明确是“当前分类全部已读”或“全部通知已读”。
- 角标显示有效未读数，`>99` 为 `99+`，归档、撤回、过期和不可访问记录不计入。
- 详情展示类型、来源、发送者、时间、所属上下文、正文和允许的操作；不展示其他收件人的邮箱或已读状态。
- 读取普通公告或校对反馈不出现“工作已完成／已接手”的假状态。

### 10.4 更新机制

- 首版采用 HTTP 轮询，不引入 WebSocket 或 SSE 服务。
- 建议前台 60 秒查询未读汇总，重新聚焦／重连时立即更新；后台降频或暂停，失败指数退避并带抖动。
- 页面卸载、退出登录和切换账号时取消请求及轮询，清理本账号数据；拒绝旧请求结果写入新账号状态。
- 详情操作后立即刷新本地状态与服务端汇总；多标签页通过安全的同源事件同步“需要刷新”，不在共享存储中传播私有正文。
- 新通知默认不打断翻译操作，不弹强制模态框、不播放声音、不自动导航。

### 10.5 与邀请／申请提醒衔接

首版拟用独立的“待处理邀请／申请”区块或快捷入口整合现有信息：

- 保留原有邀请和申请接口、原处理页面及身份判断；不改业务状态机。
- 通知“未读”与申请“待处理”分别展示，不把两者相加为一个语义混乱的未读数。
- “我”现有待处理红点保留；通知页内提供跳转，不因打开通知页消除待办。
- 将现有轮询集中管理或复用，避免 Dashboard 与通知页同时重复查询同一计数。
- 不在发布时回扫所有历史申请生成站内通知，更不补发邮件。
- 以后若决定把邀请／申请变成真正的持久化通知事件，再单列事件清单、接收者、类别和去重规则；不借本轮隐式扩展个人通知。

### 10.6 发送页面与设置

- 系统发送与全站管理放 `/admin/notifications`；团队发送放 `/dashboard/teams/:teamID/setting/notifications`；项目基础设置 `projects/:projectID/setting/base` 提供发送与记录入口。实际项目前缀沿用既有路由，不能只支持从“我的项目”进入。校对稿保留原业务操作，无阶段按钮或个人发送器。
- 编辑器提供格式按钮、名片选择器、收件人过滤／搜索、分页预览、邮件选项及正文预览。
- 普通公告提供草稿、定时、失效时间、确认发送和发送历史；发送后展示分发中／完成／部分跳过／失败汇总。
- 团队设置新增两个创建者专属开关，展示作用范围和“影响现有项目”的提示。
- 用户设置首版提供系统／团队／项目三类业务邮件偏好，注明不会阻断账号安全邮件；个人偏好仅保留底层字段和接口，随未来模块接入再启用对应 UI。

### 10.7 全站消息管理页面

- `/admin` 侧栏新增“消息管理”，主列表为 `/admin/notifications`，详情拟为 `/admin/notifications/:id`，站点发送页拟为 `/admin/notifications/new`；所有入口均要求有效站点管理员，且前端隐藏不能代替后端鉴权。
- 按通知发布意图列出全站消息，不是逐收件人重复列出同一公告。可跨范围查看标题、正文、原发送者、安全的范围标识、发布时间、发布／撤回状态和投递汇总，不限于管理员自己收发的消息。
- **筛选**：分类、事件类型／来源、团队／项目、发送者、时间区间、发布状态、撤回／过期状态、邮件投递状态；筛选选项由服务端校验，不能注入任意查询条件。
- **搜索**：消息 ID 精确查找及标题／正文纯文本关键词检索，支持中文与常见多语言文本，返回匹配摘要；管理员搜索可以命中其非成员团队／项目的通知正文，而普通收件搜索仍受本人可见性约束。
- 拟覆盖所有已保存的普通通知状态，包括草稿、定时、准备／分发中、已发布、已撤回／已过期；用户个人归档不从全站列表移除记录。个人底层分类若无数据则为空，不因此新增个人专属功能。
- 管理列表与详情保留唯一“发送站点通知”入口，编辑器按 §5.5 独立选择接收方；不得提供“以该团队／项目身份发送”“复制并代发”“恢复撤回”“人工补发他人邮件”等按钮。
- 每条可处置消息提供撤回／取消投递操作，执行 §8.4 的二次确认与审计；已撤回消息仍可查看原内容、状态和原因，但不提供恢复／重新发送、硬删除、改写正文或代收件人已读／归档操作。
- 消息列表筛选、收件方筛选和个人收件箱使用独立状态，搜索不会触发发信。管理员查看详情也不会把该消息自动标为任何人的已读。
- 查询必须分页、限流、限定关键词长度与执行耗时。P0 固化中文／多语言索引与检索方案，验证当前 MongoDB 拓扑和资源可承受，不依赖尚未部署的搜索服务，不允许用户自由正则或全库无界扫描；索引与搜索派生字段按 §12、§15 审查。

## 11. 核心架构与模块契约

### 11.1 分层

```text
通用手动发送 API / 校对稿既有入口 / 个人底层接口（未来模块）
                   │
                   ▼
    核心 NotificationService（权限、内容、收件、幂等）
                   │
       MongoDB 发布意图、名单分块、收件记录、投递记录
                   │
       可靠分发任务 + 周期恢复扫描（Celery）
             ┌─────┴─────┐
             ▼           ▼
        站内收件箱      邮件传输适配器
             │           │
        统一查询 API       SMTP
             │
        前端通知中心
```

- 上图描述普通通知路径。账号安全流程走隔离的邮件任务／传输适配，运维日志走独立告警路径；两者均不经过普通通知发布意图与收件箱，不能为了统一图示而强制依赖通知服务。
- SMTP 与 UI 不承担通知是否存在的事实来源；数据库中的发布意图和记录才是依据。
- 核心服务不导入任何具体 `app.modules.<name>`；模块可依赖核心服务，依赖方向单向。
- 全站管理查询／撤回使用独立服务授权入口，复用同一通知事实与撤回状态，不复用普通收件人过滤器，也不将管理身份注入团队／项目发布权限。
- 不把核心发送器注册成可选模块；删除所有模块目录后，通知中心和邮件仍应正常运行。

### 11.2 内部调用契约草案

```python
NotificationService.publish(
    context=trusted_context,          # 服务端构造的操作者／受信服务上下文
    category="personal",
    source="module:<module_name>",
    event_type="<module_name>.<event>",
    audience=recipient_spec,
    title="...",
    body="...",
    body_format="bbcode_v1",
    related_resources=[...],
    requested_channels={"in_app", "email"},
    idempotency_key="stable-business-operation-key",
)
```

此为个人通知等未来模块接入的**服务端底层接口草案**，首版只实现通用契约与隔离测试，不接入真实个人事件生产者；不是允许浏览器传 `trusted_context` 或 `source` 冒充系统的 HTTP 接口，也不是用户私信接口。

- 模块执行于同一后端进程，是受信代码扩展，不宣称这一接口能沙箱隔离恶意模块。
- 注册来源和允许的类型／范围，服务器构造来源上下文；前端无法覆盖这些信息。
- 用户操作驱动的模块调用继承操作者权限；受信后台个人事件只能通知由模块业务验证过的相关用户。
- 系统／团队／项目分类不是模块可以任意用来绕过发送规则的标签；授权范围须由核心检验，首版不挂接这些分类的自动业务事件生产者。通用 HTTP 发送端点仅接受人工公告，校对稿事件只能由既有业务入口构造。
- 单次业务事件应提供稳定幂等键；模块重试不能重新制造不同事件 ID 绕过去重。
- 不接收可执行前端组件、任意 HTML 或任意外部跳转脚本作为持久化通知内容。

### 11.3 模块卸载与无订阅首版

- 保存安全的基础内容、来源标识和资源引用；核心可以不加载模块就渲染通知。
- 需要模块路由的按钮只通过通用贡献注册表解析；模块不在时隐藏／禁用，并提示功能不可用。
- 模块不存在或权限无法确认时，敏感资源回退为不可访问，而非默认放行。
- 不创建订阅集合、不增加订阅按钮、不默认给用户订阅团队或项目。
- 后续订阅模块自行决定事件产生与接收关系，再调用核心服务；核心偏好与投递能力可以复用。

## 12. 数据模型与索引草案

下列为逻辑职责，可在评审后细化字段名；优先使用新的核心集合，避免破坏旧 `message` 或现有成员集合。

### 12.1 Notification（发布意图与正文）

关键字段：

- ID、schema/body 格式版本、category、source、event_type。
- actor_user_id、作用范围（team_id／project_id）、安全的关联资源 ID。
- 标题、BBCode 正文；校对稿反馈保留必要的目标语言／可选文件等业务关联，值由既有业务入口校验构造。首版不增加阶段声明字段。
- 发布状态、创建／计划／发布／失效／撤回时间、内容版本；撤回操作者、来源（范围内或全站管理）、受限理由和审计关联。
- 收件规则、名单封存标记、准备游标／恢复检查点、汇总状态。
- 幂等作用域、幂等键哈希、请求内容指纹。

索引建议：幂等作用域 + 键唯一；状态 + 到期时间；范围 + 创建时间；操作者 + 创建时间。全站分类／来源／状态／范围／时间过滤与标题／正文纯文本检索需在 P0 单列查询计划和索引；派生搜索内容与原通知保持同级访问控制，不索引安全邮件、错误日志、验证码或完整收件邮箱。

### 12.2 NotificationAudienceChunk（收件快照分块）

- notification_id、chunk_no、收件用户 ID 列表、解析状态、完成标记。
- 单块拟定 100–200 人，不能把全站用户 ID 塞入一个可能触碰 MongoDB 16 MiB 上限的文档。
- `(notification_id, chunk_no)` 唯一；名单在公开分发前封存。完成分块可以重复处理而不会生成重复收件记录。
- 封存后不再按原筛选动态追加新成员；恢复只处理同一份确定名单。

### 12.3 NotificationReceipt（每人站内收件状态）

- notification_id、user_id、发布时间／稳定排序键。
- read_at、archived_at、必要的投递和可见性元数据。
- 不在每个收件人记录复制整篇正文，避免全站公告造成大量内容重复；但读取必须检查全局撤回／失效和接收资格。
- `(notification_id, user_id)` 唯一；用户 + 发布时间／ID、用户 + 已读／归档等索引依实际查询设计。

### 12.4 NotificationDelivery（邮件 outbox）

- notification_id、user_id、channel、状态、尝试次数、next_attempt_at。
- 租约 token／到期、稳定 Message-ID、最后错误类别、受理时间、人工重试记录。
- `(notification_id, user_id, channel)` 唯一；状态 + next_attempt_at、租约到期索引。
- 按 user_id 解析当前有效邮箱，不持久化全体 To／Cc 列表；确需审计邮箱时脱敏／限制访问。
- 安全邮件不把验证码内容复用到这一普通业务 outbox；运维错误日志也不写入该集合。

### 12.5 NotificationPreference（用户偏好）

- user_id 唯一；四类业务邮件允许值、版本、更新时间。`personal` 字段与底层接口预留，首版不启用对应设置 UI 或实际事件。
- 没有文档时使用明确默认值，不需要批量给旧用户写入新字段。
- 不增加“关闭验证码邮件”开关。

### 12.6 NotificationPolicy（范围策略）

- 拟使用独立的团队通知策略记录：team_id 唯一、两个管理员开关、version、修改者／时间。
- 缺省即关闭，不修改旧身份权限默认含义，不触发历史数据回填。
- 实施时如选择复用现有身份策略容器，必须证明不会与团队标签配置互相覆盖，且不绕过创建者校验；否则采用独立集合。
- 系统通知无需新增所有者配置；管理员管理权按 R01 使用现有 `ADMIN_EMAIL`，不新增身份模型。

### 12.7 审计与容量

- 发布、撤回、策略变更、重发记录使用现有审计能力或受限通知审计；不记录正文副本、验证码、密码和 SMTP 凭据。
- 全站管理搜索／详情访问及撤回记录当前操作者、必要的对象或范围标识、时间、结果和管理操作理由；不把正文、完整关键词／筛选载荷或收件邮箱写入一般日志。管理撤回日志受限保留，不可由普通发送者改写。
- 撤回理由属于受限管理信息；普通收件人只看到通用撤回提示，全站管理详情可查看审计原因。管理员能看消息正文不代表可以读取所有用户逐人已读轨迹。
- 首版未读数从可见收件记录计算，不先引入高风险的永久冗余计数器。性能不足时再通过测试引入可修复缓存。
- 权限检查批量加载成员／项目，不逐条通知触发 N+1 查询；计数不能通过全量加载正文得到。
- 分页、预览、收件解析、管理搜索和群发都有限制和游标，不能把全站用户名单或全部消息正文放进一次 API 响应；列表只返回必要摘要，正文通过受权详情查询获取。

## 13. 可靠投递、并发与故障恢复

### 13.1 发布流程

1. 验证登录、范围权限、内容、目标、筛选规则及请求限流。
2. 用作用域内唯一幂等键持久化发布意图和请求指纹；相同键相同载荷返回原结果，不同载荷返回冲突。
3. 即时或到期后生成持久化名单分块；分块完成且封存前不公开部分名单的正文。
4. 将根事件置为可分发，投递 Celery 快速任务。RabbitMQ 不可用时，意图仍在数据库中待恢复。
5. worker 按分块幂等创建 Receipt 与 Delivery；唯一索引防止重复。
6. 分发检查点在对应写入后推进；崩溃重放不会丢失未处理分块。跨集合部分写入由恢复扫描补齐；任何恢复都不得清除全站管理撤回状态或重启已取消的投递。
7. 邮件 worker 通过原子条件更新领取租约，检查权限、偏好、有效期后发送并记录结果。
8. 所有站内分块完成后更新发布汇总；邮件状态独立跟踪。

返回 `202` 表示“发布意图已可靠受理”，不是所有渠道成功。若连意图都无法保存，返回失败而不是假成功。

### 13.2 不依赖跨文档事务

- 实施前核对 MongoDB 部署，不能在未知或单节点环境直接依赖事务。
- 根意图、分块、收件、邮件不是一次原子写入；必须通过单文档 CAS、唯一键、检查点、封存标记和恢复扫描覆盖每个崩溃点。
- 不允许“先改完工作状态再直接 `.delay()` 且没有持久化补偿”的模式。
- 首版人工公告不修改工作状态，校对稿仅按既有操作读取差异并创建通知意图；不增加阶段记录或工作流双写。
- 既有安全邮件与校对稿接入时分别验证调用失败与重试语义，不要求它们通过未经验证的通用事务装饰器。

### 13.3 周期扫描与队列

- 必须有服务端周期任务扫描人工确认的到期公告、未封存准备任务、待分发分块、到期重试与过期租约；只处理已存在的发布意图，不扫描项目／人员／进度来制造新的业务通知。
- 拟选 Celery Beat 单实例调度 + 幂等扫描任务；具体部署方式、CPU／内存和队列路由纳入部署审查。
- 扫描批次有上限，使用租约，重复扫描或两个任务竞争不能重复发布。
- 不用大量长时间 Celery ETA 消息作为唯一的定时持久层，不依赖页面访问触发恢复。
- 新增队列前确认已有 worker 会订阅；安全邮件优先级不能仅靠在没有消费者的队列里写一个路由名实现。
- 批量邮件建议低并发、可配置速率与退避；投递配额需依据 SMTP 服务限制测定。

### 13.4 exactly-once 的边界

- 可以保证业务事件、站内收件记录、逻辑邮件投递记录唯一。
- 不能在普通 SMTP 上保证“绝不重复且绝不丢失”的严格 exactly-once：服务端已接收后连接断开时，客户端可能不知道结果。
- 使用稳定 Message-ID、状态区分和保守处理降低重复风险；`unknown` 交给受控重试／人工判断，不能盲目当确定失败。
- 不通过删除旧记录再重建的方式“重试”，以免丢失审计与幂等性。

### 13.5 建议运行参数

这些是初值，不是未经测试的容量承诺：

| 参数 | 建议初值 |
| --- | --- |
| 收件列表页大小 | 默认 20，最大 100 |
| 预览页大小 | 默认 50，名单分页 |
| 名单／分发批次 | 100–200 人 |
| 前台未读轮询 | 60 秒，失败退避 |
| 恢复扫描周期 | 30–60 秒 |
| 发布限流 | 按操作者、范围、事件类型分别限制；安全邮件保留独立既有频率规则 |
| SMTP 并发／重试 | 按服务器与供应商限制配置；先低并发，瞬态错误指数退避，有上限 |
| 定时最大迟到窗口 | 1 小时，超限待处理，不盲目群发 |

## 14. API 草案

沿用项目既有认证、错误结构、分页／CORS 约定。以下列出设计契约；初版已固化的请求字段、分页和差异见实施记录，不能把尚未落地的草案接口当成可调用接口。

### 14.1 收件人与偏好

| 方法与路径 | 用途 |
| --- | --- |
| `GET /v1/me/notifications` | 分类、未读、归档筛选及游标分页，仅返回本人可见记录。 |
| `GET /v1/me/notifications/unread-counts` | 分类及总未读数量，与列表可见性一致；底层兼容 `personal`，首版不生成对应真实事件。 |
| `GET /v1/me/notifications/<id>` | 详情，包含按当前接收者权限解析的安全展示节点。 |
| `PATCH /v1/me/notifications/<id>` | 仅修改本人的已读／归档状态，不能修改正文和接收者。 |
| `POST /v1/me/notifications/mark-read` | 按明确分类批量已读，使用服务端请求开始时间截止，幂等。 |
| `GET/PUT /v1/me/notification-preferences` | 本人业务邮件分类偏好，支持版本检查；`personal` 仅保留底层支持，前端暂不启用。 |

### 14.2 普通发送与管理

| 方法与路径 | 用途 |
| --- | --- |
| `POST /v1/notifications/preview` | 系统／团队／项目人工公告的授权预览；不接受个人或伪造的业务事件，不创建投递。 |
| `POST /v1/notifications` | 人工创建系统／团队／项目草稿、定时或即时公告，校验分类权限；拒绝 `personal`，事件类型由服务端固定为 `announcement`。 |
| `GET /v1/notifications/sent` | 普通发件人仅查询可管理范围内的发送历史及汇总；全站查看／搜索必须走 §14.5 独立管理接口。 |
| `GET/PATCH /v1/notifications/<id>` | 普通范围发件详情；仅有原范围编辑权限的未发布内容可编辑且须版本校验，管理撤回／取消的记录不可恢复。 |
| `PATCH /v1/notifications/<id>`（`draft: false`） | 初版合并草稿编辑与明确发布：携带完整内容和当前 `version`，CAS 防止并发重复发布；版本冲突后读取详情确认结果。不另设 `/publish` 端点。 |
| `POST /v1/notifications/<id>/revoke` | 撤回或取消计划，返回邮件不可撤回提示。 |
| `GET/PUT /v1/teams/<id>/notification-policy` | 策略读取和创建者专属更新；权限与团队通用修改区分。 |

### 14.3 既有校对稿与名片

| 方法与路径 | 用途 |
| --- | --- |
| `POST /v1/projects/<project_id>/targets/<target_id>/send-proofread-draft` | 既有接口，不新增业务动作；内部接入 `project / proofread_feedback`，保留校对权限、参数、差异、收件及抄送规则，返回真实受理／投递状态。 |
| `POST /v1/notification-project-cards/resolve` | 有限批量解析本人可访问项目；不可访问项目统一降级。可在实现时合并进详情渲染避免重复请求。 |

首版不提供阶段通知相关 API。个人发送只允许 §11.2 的受信服务端接口，不新增对应公共 HTTP 端点，也不得通过普通发送端点改变分类或来源绕过这一限制。

### 14.4 初版人工发送请求示例

```json
{
  "category": "team",
  "scope_id": "...",
  "title": "项目募集校对人员",
  "body": "[b]募集校对[/b]\n[project]...[/project]",
  "audience": {
    "mode": "condition",
    "base_roles": ["member"],
    "worker_qualifications": ["proofreader"]
  },
  "email": false,
  "draft": false,
  "publish_at": null,
  "expires_at": null
}
```

- 幂等键通过请求头或项目既有等价机制传递，作用域包含操作者／来源，不能不同用户互相碰撞。
- 错误至少区分：未登录、无权限、非法对象／不可访问、空收件人、版本／幂等冲突、内容不合法、限流、暂时不可用。
- 资源不可访问的返回不得帮助枚举私有项目；详情响应不得携带之后才由前端隐藏的敏感原始字段。
- 预览只供确认，不成为永久发送授权；不直接接受前端渲染 HTML。

### 14.5 全站管理与站点接收方 API

全部接口要求当前有效站点管理员身份，不以“必须是消息原发送人／收件人／范围成员”限制全站查看或管理撤回；但这项授权不传递给团队／项目普通发送接口。

| 方法与路径 | 用途 |
| --- | --- |
| `GET /v1/admin/notifications` | 全站普通通知分页列表，支持 §10.7 的筛选、关键词搜索与 ID 查找；不是用户收件箱列表。 |
| `GET /v1/admin/notifications/<id>` | 管理详情，可查看跨范围标题／正文、投递汇总及撤回记录；无标记已读副作用。 |
| `POST /v1/admin/notifications/<id>/revoke` | 全站管理撤回／取消；要求二次确认所对应的显式确认值、理由、期望版本与幂等键，不编辑正文或代发。 |
| `GET /v1/admin/notification-recipients` | 站点通知候选用户的受限搜索／筛选，服务端分页，仅返回必要身份信息；不返回全量邮箱。 |
| `POST /v1/admin/notifications/preview` | 仅预览站点通知内容与筛选出的收件名单、站内／邮件人数及跳过提示；不能用于团队／项目代发预览。 |
| `POST /v1/admin/notifications` | 仅创建站点通知；服务端固定 `category=system`、`event_type=announcement` 和真实操作者，拒绝客户端指定团队／项目／个人类别或伪造来源。 |

- 站点编辑器调用专用管理前缀的预览／创建端点，底层复用通用内容、选人、幂等与邮件偏好规则，不复制一套较宽松的发布实现。
- 站点消息的团队／项目收件筛选字段只进入接收规则，不变成代表该范围发送的类别或发送者身份。普通发送端点也必须独立校验范围权限，不能凭站点管理员标记绕过。
- 管理 API 不提供对其他发送者正文／收件人的 `PATCH`、代发 `publish`、人工重发、硬删除或逐用户已读修改端点；站点草稿自身的合法编辑仍按普通发件权限校验。
- 显式确认不是仅靠弹窗显示：撤回请求必须有当前版本与确认字段，缺失／冲突／权限失效均拒绝；相同幂等键不重复撤回。字段名及理由长度在 P0 固化。

## 15. 兼容、初始化与迁移边界

### 15.1 既有迁移冻结约定

遵守 `docs/README.md`：不修改迁移运行器、不重写已应用版本、不默认新增 `0009` 或重跑 `0008`。

拟采用新集合 + 缺省策略／偏好，尽量无历史文档改写。但**新集合及索引的创建仍是需要评审的数据库变更**，不能把它伪装为“完全无需数据库操作”。

- P0 固化新集合、索引、唯一约束及容量估计。
- 使用项目现有可验证的索引初始化惯例；提前检查索引冲突和空集合初始化，不擅自写一个替代迁移运行器。
- 需要历史数据搬迁、已有集合新增强制字段、唯一索引清理或站点所有者回填时，先提交专项方案并获批。
- 禁止为兼容新功能删除旧集合、旧索引或业务记录。

### 15.2 旧 Message 数据

- 先统计是否实际存在记录及是否被旧接口消费，只读盘点，不将内容输出到公开日志。
- 首版默认不迁移、不补发、不删除；若有必须保留在新 UI 中的历史记录，另设计只读兼容或迁移审查。
- 不根据模型存在就断言生产库为空。

### 15.3 旧邮件任务与接口

- 新旧发布短暂共存时，旧队列中的 `tasks.email_task` 名称、参数和模板仍可消费。
- 旧业务入口接入后只有一个主投递路径，不能同时调用旧 `send_email` 与新 outbox 导致双发。
- 没有部署新版消费者前，不投递新版专属任务到生产队列。
- 回滚时先停新发布／调度，处理或保留新任务，不能让旧 worker 静默丢弃未知任务。

### 15.4 上线边界

- 不创建或回填项目阶段状态；不自动为当前或历史邀请／申请等业务生成通知，不向历史用户补发校对稿，不接入个人事件生产者。
- 新功能首启默认管理员开关关闭，普通群发邮件默认未勾选；站点收件方需显式选择，不因进入全站管理页面自动选中全体。
- 全站管理仅查看核心通知已保存的记录；不为“看全部”回填旧 `Message`、安全邮件、日志或历史业务，也不新增个人事件生产者。
- 通知核心的发布总开关可用于发布／运维停发，不是可选模块开关；停发普通通知不能停用密码重置邮件或被误认为关闭了独立运维告警。
- 开发环境邮件必须限于批准的测试收件人或测试 SMTP，不得沿用真实全站收件列表做验收。

### 18.5 验收样例

1. 团队创建者发布只给普通成员中具备校对资质的招募，插入项目卡片；有／无项目权限两名用户看到不同卡片结果。
2. 有公告发送权限的项目创建者手工编写项目消息，筛选校对职位并确认发送；没有阶段选择／完成按钮，项目与译文状态保持不变。
3. 默认项目管理员不能发普通公告，团队创建者开启开关后可以；团队管理员不能自行开开关。
4. 一名收件者无邮箱、一名退订、一名开启邮件：三人均有站内通知，只有符合条件者有业务邮件。
5. 关闭 RabbitMQ 后接受发布，恢复后完成站内分发；模拟 SMTP 接收后断开，界面不错误保证“零重复”。
6. 邀请待办仍在，打开通知中心不将其视为已处理。
7. 用受信模块测试夹具验证底层接口；在隔离副本移除模块后，测试通知仍可阅读安全基础内容，模块按钮不可用但页面不崩溃；不为此接入真实个人事件。
8. 校对者通过原入口寄送有差异的稿件；活跃翻译收到站内通知，邮件逐人投递，操作者抄送去重；无翻译时可只给自己，无差异时仍拒绝。
9. 关闭普通项目邮件后密码重置仍可按安全流程发送；独立测试错误日志告警，不在通知中心或全站管理出现日志或验证码。
10. 非团队成员的站点管理员在 `/admin/notifications` 搜索到该团队消息并查看正文；不能代发或编辑，二次确认并填写理由后可撤回，用户收件隐藏而管理审计仍在。
11. 管理员在全站管理处新建站点通知，筛选某团队中的非站点管理员或手选用户；预览正确、仅命中者收到，消息类别仍为系统，邮件尊重系统偏好。
12. 取消撤回确认框不影响消息；确认前降权或他人改变状态后提交会被拒绝／要求刷新，不能使用过期确认继续处置。

## 19. 开发部署、观测与回滚

### 19.1 部署前门槛

- 完整通知计划已批准（R01 已确认），P1–P5 通过，工作区仅包含本需求明确变更。
- 两仓库仍在 `dev`，重新核对 `main` 未改；记录提交 SHA 和构建来源。
- 检查开发环境变量、`ENABLE_USER_EMAIL`／`ENABLE_LOG_EMAIL` 两个开关、错误／回复邮箱的实际配置读取、两条 SMTP 路径的测试收件保护、队列和调度实例数量；不打印秘密。
- 备份数据库／配置并验证恢复方法，记录当前 release、镜像与新集合初始化清单。
- 现有开发部署脚本会清理部分旧 release／镜像，回滚副本必须放在其清理范围之外并保留独立镜像标签。
- 新增数据库操作如超出 §15 已批准范围，暂停部署并另行审查，不能直接加迁移版本补救。

### 19.2 发布步骤草案

1. 先以普通通知发布关闭、开发邮件受保护状态部署兼容后端与消费者。
2. 验证新集合索引、旧邮件任务、通知 API 和权限拒绝行为。
3. 启动经批准的扫描调度，确认任务队列有实际消费者、无重复调度造成的异常。
4. 部署匹配前端，验证旧功能与移动导航。
5. 使用专门的测试账户／团队／项目开启通知并做小规模端到端验证。
6. 检查测试邮箱、站内数量、失败／跳过汇总及权限变更后的历史可见性。
7. 执行现有开发环境 Verify 流程，并人工验证新功能；自动健康检查不能代替通知业务验收。
8. 向用户提供开发地址、release、截图、已知限制，等待效果审查；不部署生产。

### 19.3 观测指标

- 发布受理量、拒绝／限流量、收件解析耗时、积压意图数。
- 待分发分块、待投递／重试／未知状态邮件数、最老等待时间。
- SMTP 受理率／错误类别、因偏好／邮箱／权限跳过数量。
- 恢复扫描执行时间、租约回收次数、队列消费心跳。
- 未读查询、普通／全站管理列表与搜索延迟、数据库查询次数、内存和批量操作峰值；记录管理查询授权拒绝、撤回受理／冲突／失败计数，不记录敏感查询文本。
- 仅记录必要 ID、计数和错误类别；不把正文、验证码和完整邮件地址写入一般日志。

### 19.4 回滚顺序

1. 先停普通通知新发布与定时扫描，保留站点安全邮件及独立运维错误告警原有能力。
2. 决定正在处理的新任务是由兼容 worker 排空，还是暂停并保留；不能让旧 worker 消费不认识的任务。
3. 切回已保存的前后端 release 和部署配置，确认旧 API、登录、密码重置、项目操作可用。
4. 保留新增通知集合和投递记录，不删除新数据来“恢复旧版本”。后续重新启用前核对未完成任务，避免重复邮件。
5. 已被 SMTP 接受的邮件不能通过回滚收回；将实际投递情况列入回滚记录。
6. 发布修复后先对照旧幂等键、Message-ID 和投递状态做恢复验证，再开启普通群发。

## 20. 风险清单与批准清单

### 20.1 主要风险

| 风险 | 控制措施 |
| --- | --- |
| 管理管理员、全站消息管理与范围发送权限混用 | R01／R02 明确：管理员身份管理仅站长，全站消息查看／确认撤回及站点发送允许有效站点管理员，但不授予团队／项目代发权；独立测试。 |
| 团队管理员继承项目权限导致默认可群发 | 新通知权限单独判定，角色矩阵和 API 越权测试。 |
| 通用入口越界成自动工作流或个人私信 | 不提供阶段 API；普通公告限定人工入口，个人仅受信底层接口，拒绝伪造分类／事件来源。 |
| 名片或缓存泄漏私有项目 | 发送者／接收者双重检查、服务端脱敏、按用户隔离、邮件降级。 |
| 停机或双写故障丢通知 | 持久化意图、分块、检查点、唯一约束、周期修复。 |
| 全站误撤回、滥用或撤回后继续投递 | 逐条二次确认、理由／版本／幂等校验、受限审计与状态 CAS；worker 重查，不能恢复已撤回记录。 |
| 全站搜索泄漏或拖垮数据库 | 独立实时管理授权、中文检索实测、分页／索引／限流／耗时上限；隔离摘要缓存，不搜索安全或运维载荷。 |
| SMTP 不确定结果重复寄送 | 独立 unknown 状态、稳定 Message-ID、保守重试，不承诺 exactly-once。 |
| 批量公告妨碍账号安全邮件 | 分流、限速、明确队列消费者和优先级实测。 |
| 旧邮件与新投递同时运行导致双发 | 每个入口单一主路径、兼容旧排队任务、部署顺序测试。 |
| 迁移冻结约定被新功能绕开 | 新集合／索引明示评审；需要历史改写时单独批准。 |
| 开发部署向真实用户发信 | 两条 SMTP 路径均使用测试 SMTP／收件人保护；不能只依赖 DEBUG，核对两个独立开关，小范围验收。 |
| 运维日志泄漏或告警递归／邮件风暴 | 独立运维收件与开关，不进普通通知集合；明确错误地址配置、失败隔离与限流。 |
| 邮箱验证状态假设导致误发或阻断账号流程 | P0 固化正常／历史／初始化账号规则，不擅自改旧数据，安全邮件例外单测。 |
| 通知功能挤压移动布局 | 四项底栏、长内容断行、320px 验收、保留现有主题与预览修复。 |
| 首版无自动清理造成持续增长 | 记录容量、分块限量、日志限期；业务记录保留策略以后经审查调整，不自动删用户数据。 |
