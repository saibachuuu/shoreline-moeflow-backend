## 1. 目标、状态与范围

### 1.1 目标

建设独立于可选模块的**核心通知服务与通知中心**，统一管理站内通知和邮件投递。支持系统、团队、项目、个人四个展示分类；后续模块可调用核心接口，但核心不得依赖具体模块。

本文中的状态标记：

- **已确认**：用户已经明确提出的要求。
- **拟采用**：用户授权设计者决定的实现细节，或用于填补边界的建议；仍供本轮审查，不等于已经批准或实现。
- **待决策**：存在实质性身份或权限歧义，实施相应功能前必须确定。

### 1.2 已确认要求

| 编号 | 要求 |
| --- | --- |
| C01 | 通知系统属于核心功能，不作为 `modules` 模块安装。 |
| C02 | 首版渠道为站内通知和邮件通知；现有邮件能力应纳入统一体系。 |
| C03 | 系统通知仅面向注册用户，不建设访客通知 UI。 |
| C04 | 系统通知仅有效站点管理员可发送，不区分环境变量指定或手动授予；普通团队、项目通知默认仅创建者可发送。 |
| C05 | 团队创建者可允许团队管理员发送团队通知，也可设置项目通知默认权限是否包括项目管理员。 |
| C06 | 项目阶段通知仅在具备对应职位权限的用户手动确认后发送，不根据进度或其他事件自动发送。 |
| C07 | 团队、项目通知支持全员、管理身份、工作人员资质／职位和指定成员筛选。 |
| C08 | 团队募集是团队内部为某个项目募集人员，不向团队外或全站群发招募。 |
| C09 | 外部人员记录跳过；不做用户私信。 |
| C10 | 个人通知留给后续模块接入；首版不做订阅产品功能，仅预留接口。 |
| C11 | 桌面端入口在左下角用户元素上方；移动端入口仅出现在底栏的“团队”和“我”之间。 |
| C12 | 保留此前移动端右上角的主题快捷开关，以及“我”内的主题、CDN 设置。 |
| C13 | 通知内容包含标题、正文，提供基础 BBCode 与可访问项目的名片展示。 |
| C14 | 通知系统先审查计划再实施；实际改动在 `dev`，不得直接影响 `main`。 |
| C15 | 单独先行收紧站点管理员身份管理：仅 `ADMIN_EMAIL` 指定且仍为有效管理员的站长可授予／取消管理员，其他管理功能不变。 |

### 1.3 首版拟包含

- 收件箱、详情、未读数量、分类、归档、通知偏好。
- 团队／项目发送器，收件人预览，创建者控制的发送权限设置。
- 受限的手动“阶段完成”通知入口。
- BBCode 编辑、预览、项目名片与逐接收者权限校验。
- 普通公告的即时／定时发送、失效与撤回。
- 持久化投递记录、异步邮件、重试、幂等及故障恢复。
- 校对稿业务邮件接入；账号安全邮件共用投递基础设施但与普通通知隔离。
- 邀请／申请提醒与通知入口的衔接，具体策略见 §10.5。
- 模块调用契约及零模块运行验证。

### 1.4 明确不做

- Web Push、浏览器系统通知、短信、即时通信、私信、评论和回复。
- 自动识别翻译完成、自动进入下一阶段、任务依赖图、人员逐一签收、完整工作流引擎。
- 文件／文件夹／批次级阶段状态管理；首版阶段范围见 §6。
- 团队外招募、全站关注流、订阅页面、自动订阅及订阅对象管理。
- 任意 HTML、附件上传、远程图片嵌入、任意 iframe、插件可执行通知内容。
- 对旧业务记录无差别回填通知、补发历史邮件。
- 借本功能重构既有迁移体系或改变现有项目完成／重开规则。

## 3. 审查决策表

### 3.1 已确认的站点身份规则与先行修复

**R01 已确认（2026-10-05）：系统通知由所有有效站点管理员发送，不区分管理员来源。**

用户在知悉原有后台可以授予其他用户站点管理员身份后，明确要求将两个权限分开：

| 操作 | 允许身份 |
| --- | --- |
| 授予／取消站点管理员 | 只有当前服务端 `ADMIN_EMAIL` 指定且仍为未封禁站点管理员的账号（站长） |
| 发送站点通知 | 所有有效站点管理员，包括站长和站长手动授予的管理员 |
| 其他已有站点管理功能 | 保持现状，不因“站长”区分一并收紧 |

实现边界：

- 原主分支的用户管理界面与 `PUT /v1/admin/admin-status` 确实支持添加／取消管理员，本次不是删除这个功能，而是收紧调用者资格。
- 站长资格由后端运行时配置及当前数据库账号状态计算，不新增角色字段或历史迁移；不能信任前端传入的邮箱、布尔权限或 JWT 中缓存的旧身份。
- 原有 `admin_can()` 语义保持不变，未来站点通知使用有效站点管理员判断，不错误复用“管理管理员”的站长专属检查。
- 前端只获得自身的 `can_manage_site_admins` 能力，不下发 `ADMIN_EMAIL` 配置。普通管理员不显示授予／取消操作，直接请求同样拒绝。
- 配置缺失／空值、账号不匹配、已经降权或封禁时，不授予管理员管理权。
- 修改 `ADMIN_EMAIL` 后特殊管理权随生效配置切换；旧账号仍可能保留普通管理员身份和站点通知发送权。
- 原管理员初始化行为不改，站长改邮箱或取消自身管理员身份的恢复仍由运维配置／初始化负责。
- **“其他不变”的安全边界**：原有重置用户密码等高权限能力继续保留，包括可能作用于站长账号；因此此修复不等于建立了完全隔离、不可被其他管理员间接接管的站长安全层。若需保护这些路径，应另行确认范围。

这项小修复可以先行实施；**完整通知系统仍需审查本文其余内容后明确批准执行**。

### 3.2 拟采用的设计决策

审查者可按编号修改；未修改且整体批准后才作为实施依据。

| 编号 | 拟采用方案 | 原因／边界 |
| --- | --- | --- |
| D01 | 团队的两个管理员发送开关默认关闭，修改后实时适用于团队及现有项目；首版无项目级覆盖。 | 简化权限解释，避免“默认”只影响新项目而产生隐含历史差异。 |
| D02 | 项目普通通知发送者是实际项目创建者或经允许的实际项目管理员；团队管理员身份不自动等于项目管理员。 | 避免继承权限越界。团队创建者管理策略不等于自动获准冒用项目发送身份。 |
| D03 | 阶段确认独立于普通公告权限；只允许确认本人被授予的阶段，管理身份不自动获得代确认能力。 | 不把工作按钮变成普通群发后门。代确认如需支持，应另行显式授权。 |
| D04 | 阶段范围为整项目或项目目标语言；翻译／校对默认按语言，不建立文件级或自动依赖状态机。 | 兼顾多语言而控制首版范围。 |
| D05 | 基础身份条件与资质／职位条件取交集；同一条件内多个值取并集；手选成员与条件模式二选一。 | 使筛选结果可解释，不隐式扩张收件人。 |
| D06 | 普通业务通知站内必发，邮件由发送者勾选且遵守接收者分类偏好；新建普通通知的“同时发邮件”默认不勾选。 | 避免上线即产生邮件轰炸；校对稿原有邮件动作单独保留。 |
| D07 | 用户普通邮件偏好默认开启，但不提供绕过退订的“强制邮件”；安全邮件例外。 | 保持可控的通知体验。 |
| D08 | 桌面端采用完整通知页面而非浮层；进入列表不自动已读，打开详情才已读。 | 长正文、名片和历史检索更容易使用。 |
| D09 | 普通公告支持定时／失效／撤回；阶段完成即时发送，不定时。已发布内容不可原地编辑。 | 避免篡改已经完成交接的事实。 |
| D10 | 首版不自动删除历史收件箱数据，用户可归档；调试投递日志拟保留 30 天，审计只保留必要元数据。 | 先避免意外数据丢失，后续按容量审查业务记录保留期。敏感安全载荷另按短期规则处理。 |
| D11 | 首版只将邀请／申请的既有待办入口整合进通知中心，不新增未经确认的邀请类邮件或个人订阅事件。 | 不扩大“个人通知留给后续模块”的范围，也避免读过通知就丢失待办提示。 |
| D12 | 普通通知只发给发布时确定的收件人；新加入／新注册用户不自动收到此前公告。 | 首版避免混入公告订阅流和历史补发。若需“有效公告对后来者可见”，另加明确需求。 |
| D13 | 团队／项目通知失去原接收范围资格后隐藏正文和预览；卡片另行按当前项目访问权限解析。 | 防止通过旧收件箱继续读取内部信息。 |
| D14 | 批量发件只向发送者展示投递汇总，首版不提供“具体谁读过”的逐人跟踪 UI。 | 减少成员隐私暴露。名单预览用于发送确认，不等于已读追踪。 |

## 4. 分类与发送权限

### 4.1 分类不是来源

- `category`：`system`、`team`、`project`、`personal`，决定通知中心分类。
- `source`：核心或模块的稳定来源标识，用于审计和展示。
- `event_type`：如 `announcement`、`stage_completion`、`proofread_feedback`；模块使用命名空间事件标识。
- 分类、来源、渠道分别建模。模块产生的内容不应全部挤进一个“模块”分类。
- 核心允许未来模块调用，但不提供匿名或任意前端用户都能指定接收者的通用群发接口。

### 4.2 权限矩阵

| 行为 | 系统 | 团队 | 项目 |
| --- | --- | --- | --- |
| 普通公告发送 | 所有有效站点管理员（R01 已确认） | 创建者；开关开启后管理员 | 创建者；开关开启后实际项目管理员 |
| 修改管理员发送开关 | 不适用 | 仅团队创建者 | 由所属团队创建者在团队设置中控制 |
| 阶段完成 | 不适用 | 不适用 | 有该阶段职位／专属确认权限的有效项目成员 |
| 发件预览／查询可选成员 | 同发送权限 | 同发送权限，限当前团队 | 普通公告同发送权限；阶段预览走受限的阶段权限 |
| 撤回 | 原发送者且当前仍有权限，或对应范围创建者 | 同左 | 同左；阶段撤回不是撤销业务状态 |
| 查看收件箱 | 仅自己的收件记录 | 同左，并检查范围资格 | 同左，并检查范围资格 |

新权限代码名称在实现时确定。**不能只把 `SEND_NOTIFICATION` 加入已有宽泛管理员权限集合**：现有团队管理身份会继承项目权限，必须经过通知专用策略判断。

管理策略更新使用期望版本进行并发检查，记录操作者、旧值、新值、作用范围。管理员即使拥有普通团队设置编辑权限，也不得修改这两个创建者专属开关。直接构造 API 请求必须得到同样的拒绝。

预览、提交、定时到期及实际分发阶段分别进行相应权限检查。权限被收回时不能凭旧页面或旧预览 token 继续群发。

## 5. 收件人选择与权限变化

### 5.1 范围定义

- **系统**：有效的注册账户；跳过已删除、封禁账户。不要求有邮箱才能收到站内通知。
- **团队**：当前团队有效注册成员。管理人员包含创建者／管理员；普通成员是非这两类的有效成员。资质按 `worker_qualifications` 筛选。
- **项目**：当前项目实际有效注册成员；按项目标签筛选。只有团队访问继承而没有实际项目成员记录的人，不默认属于“项目全员”。
- `invited` 不是正式接收成员；`removed`、未注册外部人员不计入接收者。
- 允许发送者在所选范围内收到一份自己的通知；不自动额外抄送，校对稿现有“抄送自己”单独保留。
- 不存在资格匹配者时禁止发布空通知，提示调整筛选或分配人员；不自动找管理员补发。

### 5.2 筛选语义

```text
condition 模式：
  有效范围成员
  ∩ 基础身份条件（条件内 OR）
  ∩ 资质／职位条件（条件内 OR）

manual 模式：
  手选 user_ids ∩ 有效范围成员
```

- “全员”不与其他筛选条件同时提交，防止 UI 与后端解释不一致。
- 手选模式不得携带范围外账户；后端拒绝非法选择，而不是扩展权限。提交后失效的原有效成员可从实际发送名单中剔除并报告数量。
- 预览返回可发送人数、分页名单、外部／失效成员剔除提示。查询和人数本身也受权限控制。
- 前端不下载全站用户列表再自行筛选；所有成员搜索都必须限定团队或项目。

### 5.3 快照与时点

- 即时发送：后端重新解析并持久化接收名单。**持久化名单完成**后称为收件人快照；不宣称跨 MongoDB 多批查询获得了原子的历史成员快照。
- 定时发送：保存筛选规则，页面明确提示“人数在实际发送时重新计算”；到期检查发送权限后生成名单，不使用过时预览直接投递。
- 名单固化后，重试不得把后来加入的成员不断追加进同一通知。
- 实际投递时再剔除已失效资格的接收者；剔除只能缩小名单，不能扩大。
- 后来注册／加入者不补发旧通知。未来如需要有效公告墙，应与个人收件箱分开设计。

### 5.4 权限失效后的读取

- 读取团队／项目通知须同时验证收件人归属和当前范围资格，不仅校验收件记录中的 user_id。
- 已退出团队、被移出项目、源项目删除时，不继续返回标题、正文、摘要、封面、原始 BBCode 或搜索片段。
- 可以保留一个不含敏感信息的“关联通知已不可访问”占位，默认不计入未读数；列表与未读统计使用同一可见性规则。
- 撤回、过期、失去权限均不能收回用户以前已经看见、截图或收到的邮件；UI 不做此类承诺。
- 发送者手工写入正文的信息无法通过卡片权限机制自动脱敏；发送预览需要提示“正文对选定接收者可见”。

## 6. 手动阶段完成与交接

### 6.1 业务含义

首版的“阶段完成”是一次**有权限约束、可审计的人工交接声明**，不是工作流状态机，也不自动核实每一位工作人员都完成。

界面提示建议使用：“我确认所选范围的本阶段工作已完成，并通知选定人员继续处理。”不能把按钮含义写成“系统已验证全员完成”。

### 6.2 操作流程

1. 在项目工作区域显示“阶段完成”按钮；仅有可确认阶段的用户可操作。
2. 拉取后端计算的可确认阶段／职位列表，不能仅依赖前端缓存标签。
3. 选择阶段及范围。翻译／校对按项目目标语言选择；语言无关岗位可选整项目。首版不增加文件范围选择器。
4. 选择接收职位或具体项目成员；可推荐校对／嵌字等常见对象，但必须由操作者确认，不自动沿固定职位顺序广播。
5. 系统生成受保护的标题、项目关联、阶段、范围、确认人，允许填写补充说明；不能任意改成系统公告或替换为其他项目。
6. 显示站内人数及预计邮件人数，明确邮件可能因用户偏好而被跳过。
7. 二次确认并提交带幂等键的请求。
8. 返回“已受理／投递中”，可查看最终分发结果，不把异步 SMTP 受理伪装成所有用户已经收信。

### 6.3 不发生的副作用

- 不改变 `ProjectStatus`，不调用现有整项目完成／清空接口。
- 不锁定编辑，不新增自动依赖和“下一阶段已开始”状态。
- 不因为读取通知改变任何工作状态。
- 项目已完成、已清空或正在清空时禁止新增阶段完成声明；普通公告是否可用依照独立通知权限，不顺带修改现有生命周期权限。
- 管理身份不默认代确认他人的阶段；需要代确认时作为单独可审查扩展。

### 6.4 重复与更正

- 网络重试或同一次提交的双击复用幂等键，不重复生成通知。
- 相同人、项目、阶段、语言近期有成功记录时提示已有记录，但不能永久禁止返工后的再次交接。
- 真正再次发送须显式确认，使用新操作 ID，并可关联前一次记录。
- 发布后的阶段内容不原地修改；可发更正通知。撤回只影响通知展示，不声称撤销了系统内不存在的阶段状态。

## 7. 通知内容、BBCode 与项目名片

### 7.1 内容与约束草案

| 项目 | 拟定首版限制 |
| --- | --- |
| 标题 | 纯文本，1–200 字符 |
| 正文 | 最多 10,000 字符，限制解析节点数和嵌套深度 |
| 格式 | BBCode v1，纯文本通知视为其子集 |
| 单条项目名片 | 最多 5 个不同项目，重复引用可复用解析结果 |
| 附件／远程图片 | 首版不支持 |
| 语言 | UI 文案进入现有国际化机制；用户正文保持原文，不自动翻译 |

以上是审查默认值，应以实际移动排版和性能测试校正，不因前端限制而省略后端限制。

### 7.2 BBCode v1

支持：`[b]`、`[i]`、`[u]`、`[s]`、`[quote]`、`[list]`／`[*]`、`[url=...]`、`[project]...[/project]`。

```text
[b]《示例项目》募集校对人员[/b]

[project]本站项目ID或完整项目链接[/project]

[list]
[*]募集职位：校对
[*]工作范围：简体中文
[/list]

[quote]有意参与的团队成员请联系项目负责人。[/quote]
```

- 不支持任意 HTML、脚本、样式、远程嵌入、事件处理器和自动执行。
- 链接只允许明确的安全协议（首版 `https`／`http`）；拒绝 `javascript:`、`data:`、`file:` 等。
- 优先评估复用现有 `src/utils/bbcode.tsx` 的解析与安全 URL 能力，以通知专属选项／白名单补齐列表、引用、项目标签和复杂度限制；不改变其他页面原有标签策略。采用结构化解析，不以简单正则替换后直接拼接 HTML。前端使用 React 节点渲染，邮件使用受控模板并转义。
- 未知标签按普通文本显示；无法安全恢复的嵌套、超深、超长内容给出校验错误，防止解析耗时攻击。
- BBCode 保存格式版本；前后端共用测试样例，确保预览、详情、邮件降级语义一致。

### 7.3 编辑与项目插入

- 提供基础工具栏及预览，不要求用户记忆 BBCode。
- “插入项目”在用户当前可访问的项目内搜索；选中后保存稳定项目 ID，而非固化封面签名 URL。
- 粘贴**独立的本站项目链接**时给出转换名片提示；普通行文内链接不强制变成大卡片。
- 仅识别配置允许的本站源与已知项目路由，CDN／备用网址由通用站点配置归一化，不硬编码当前开发域名。
- 不请求用户粘贴的任意服务器来抓取标题／封面，避免 SSRF、开放重定向和信息泄漏。

### 7.4 项目名片权限

1. 插入／发布时，发送者须有项目访问权限；不能通过猜测 ID 获取项目名称。
2. 阅读时，以**接收者当前身份**批量解析项目元数据；不能把发送者的预览结果缓存后发给所有人。
3. 无权访问、项目删除、权限查询失败时，统一降级为“关联项目不可访问”，不区分错误原因泄漏存在性。
4. 降级时响应中也不得携带名称、封面、团队名、目标语言等隐藏数据，不仅是 CSS 隐藏。
5. 名片本身不授予加入或访问权限；团队招募依旧使用现有申请／邀请流程。
6. 缓存必须按接收者及权限变化隔离；不能共享包含私有元数据的 HTML。封面沿用现有受控 URL 获取机制。
7. 前端身份切换、退出登录时清除通知和名片缓存。

### 7.5 邮件降级

- 普通通知邮件优先展示通用通知类别、发送时间、简短提示和站内详情链接；默认不复制私有团队／项目的完整正文与自定义标题。
- 系统公告可渲染经转义的正文；私有业务正文完整邮件展示若需要，应作为额外披露策略审查。
- 项目名片在邮件中降级为不泄露名称／封面的“登录后查看关联项目”链接。
- 邮件同时生成 HTML 和纯文本版本，外链及换行有明确回退。
- **校对稿反馈是既有例外**：保留现有详细差异正文，明确其一旦发送就无法撤回；不得用普通通知隐私降级悄悄删除原有业务内容。

## 8. 通知生命周期

### 8.1 发布状态

拟采用：`draft` → `scheduled` 或 `preparing` → `dispatching` → `published`。

- `draft`：可编辑、预览，不生成收件记录或邮件。
- `scheduled`：可在执行前修改／取消；到期重新检查发送权限和收件人。
- `preparing`：请求已可靠保存，正在解析／固化名单；还未对接收者公开。
- `dispatching`：名单已封存，分批生成收件和投递记录；可能部分完成。
- `published`：站内分发完成，邮件可能仍在独立重试；不能把此状态解释成全渠道成功。
- `cancelled`／`failed`：未发布或未能继续发布，原因可供有权限的发送者查看。
- `revoked_at`、`expires_at` 为独立可见性字段，避免用一个状态混合发布、过期和邮件成败。

阶段完成使用即时流程，不提供草稿定时队列；可在本地保留编辑状态，但不承诺离线发送。

### 8.2 时间与定时

- API 使用带时区的 ISO 8601，服务端统一存 UTC，前端按用户／浏览器时区展示，并在定时确认处显示明确时区。
- 校验 `expires_at > publish_at`，过期通知不继续扩散，不计入普通未读角标；历史可以显示失效标记。
- 维护公告需提前发送；系统关停后，本站无法继续接收请求或投递新邮件，不能宣传为停机期间的独立告警系统。
- 定时任务因停机迟到时先检查过期时间；超过拟定最大迟到窗口 1 小时的公告标记待处理，不盲目在维护结束后大量补发。
- 启用定时必须一并部署可靠的周期扫描，不以浏览器在线或有人访问网站为触发条件。

### 8.3 撤回与归档

- 撤回操作记录操作者、时间和理由，站内隐藏原内容或显示撤回占位。
- 尚未发送的邮件尽力取消；已经被 SMTP 接受、正在发送的邮件无法保证撤回，操作页面明确提示。
- 用户归档只修改自己的收件箱，不删除其他人的通知或发送审计。拟定“归档并标记已读”，不让隐藏归档项持续占用角标。
- 首版没有用户硬删除全局事件接口，没有批量清空后台审计功能。

## 9. 站内与邮件渠道

### 9.1 普通通知渠道选择

```text
站内投递 = 有效收件资格
普通邮件投递 = 发送者选择邮件
             AND 接收者对应分类允许邮件
             AND 有有效的已验证邮箱
             AND 实际发送时仍有接收资格
             AND 未撤回／未过期
```

- 业务邮件不接受前端传任意 `to_address` 绕过用户收件资格。
- 无邮箱、未验证邮箱、关闭邮件偏好时，站内照常发送；记录邮件跳过原因，不当作投递故障无限重试。
- 账号安全邮件发送到验证流程规定的目标地址，不受“必须已验证”规则阻断。
- 邮箱地址在真正投递时从当前账号解析，并核对有效性；不向已被用户解除绑定的旧邮箱重试业务邮件。
- 普通邮件偏好关闭后，仍未投递的业务邮件要重新检查并跳过。

### 9.2 现有校对稿反馈接入

- 保留 `send-proofread-draft` 既有接口和用户操作、现有校对权限校验、语言／文件范围、无变更提示、正文差异信息与抄送选择。
- 收件人沿用原有业务规则，再做有效注册用户和邮箱校验；不因普通项目公告权限默认关闭而禁用原有校对功能。
- 按一次明确操作创建 `project / proofread_feedback` 通知记录，站内通知可查看／进入原有业务上下文。
- 默认请求邮件，符合用户点击“寄送校对稿”的语义；但尊重普通项目邮件偏好。若全部因偏好被跳过，返回并展示明确提示，不能显示“邮件已寄送”。
- 各接收者独立投递，不在 To／Cc 头公开其他用户邮箱。“抄送自己”保留为给操作者的一份独立投递并去重。
- 实施前针对旧模板确认是否含发件人邮箱和其他个人信息；既有披露须在发送预览中清晰呈现，不能意外扩大。

### 9.3 安全邮件隔离

- 邮箱确认、修改邮箱、密码重置：继续由安全流程决定接收目标、验证码有效期及重发频率。
- 不生成含验证码／重置链接的普通通知事件、站内收件记录、可检索业务日志。
- 共用邮件传输、错误分类与可观测性，但使用独立业务类型和优先处理路径；批量公告不得挤占密码重置处理能力。
- 重试前检查验证码是否仍有效，过期或已使用则停止；不重复寄送已经失效的秘密。
- 只持久化必要关联 ID／状态；敏感载荷不能出现在管理员通知详情、错误堆栈、调试输出或普通队列诊断截图。
- 如果底层邮件任务必须短期携带敏感载荷，应限制消息保存和结果记录，保证日志脱敏，不复制到普通通知 outbox。

### 9.4 邮件状态

建议：`pending`、`leased`、`accepted`、`retry_wait`、`skipped`、`failed`、`unknown`、`cancelled`。

- `accepted` 只表示 SMTP 服务接受，不表示到达收件箱或用户已阅读。
- SMTP 拒绝、连接前失败、接收后超时应区分。最后一类可能已经发出，标记 `unknown`，不承诺自动重试绝无重复。
- 未配置邮件或 `ENABLE_USER_EMAIL` 关闭时，明确显示未投递／渠道不可用，不伪报成功。
- 密码、验证码、SMTP 凭据、完整邮箱列表不进入发件汇总日志。

## 10. 前端交互

### 10.1 桌面端

- 通知入口固定在侧栏底部用户元素上方，位于可滚动团队列表之外。
- 展开显示图标、文字、未读角标；折叠显示图标、角标和键盘可访问的提示。
- 点击进入 `/dashboard/notifications`，不使用容易被长内容挤压的弹出浮层。
- 不修改现有桌面主题、CDN 模块设置和用户菜单行为。

### 10.2 移动端

底栏顺序固定为：**项目｜团队｜通知｜我**。

- 通知入口仅由现有底栏承载，不向项目预览、翻译器等无底栏页面额外插入铃铛。
- 通知首页加入移动 Tab 页识别，使进入通知首页后底栏继续存在。
- 通知详情、发送页采用普通二级页：返回按钮，按现有规则不显示底栏；保留这些页面原有的右上角主题快捷开关。
- “我”内现有主题和 CDN 设置不移动、不删除。
- 考虑 iOS 安全区、软键盘和窄屏；项目原有两列缩略图与响应式工具栏不回退。

### 10.3 收件箱与详情

- “全部／系统／团队／项目／个人”分类；个人分类首版可显示清晰空状态，不伪造订阅入口。
- 未读筛选、按最新发布时间排序、游标分页、逐条标记已读／未读、全部已读、归档及已归档列表。
- 进入列表不自动已读；详情成功加载后才提交已读。不可访问或加载失败不执行误导性成功动作。
- 全部已读以请求时的截止位置为界，不把并发刚到达的新通知一并清空。按钮明确是“当前分类全部已读”或“全部通知已读”。
- 角标显示有效未读数，`>99` 为 `99+`，归档、撤回、过期和不可访问记录不计入。
- 详情展示类型、来源、发送者、时间、所属上下文、正文和允许的操作；不展示其他收件人的邮箱或已读状态。
- 读过阶段通知不出现“工作已完成／已接手”的假状态。

### 10.4 更新机制

- 首版采用 HTTP 轮询，不引入 WebSocket 或 SSE 服务。
- 建议前台 60 秒查询未读汇总，重新聚焦／重连时立即更新；后台降频或暂停，失败指数退避并带抖动。
- 页面卸载、退出登录和切换账号时取消请求及轮询，清理本账号数据；拒绝旧请求结果写入新账号状态。
- 详情操作后立即刷新本地状态与服务端汇总；多标签页通过安全的同源事件同步“需要刷新”，不在共享存储中传播私有正文。
- 新通知默认不打断翻译操作，不弹强制模态框、不播放声音、不自动导航。

### 10.5 与邀请／申请提醒衔接

首版拟用独立的“待处理邀请／申请”区块或快捷入口整合现有信息：

- 保留原有邀请和申请接口、原处理页面及身份判断；不改业务状态机。
- 通知“未读”与申请“待处理”分别展示，不把两者相加为一个语义混乱的未读数。
- “我”现有待处理红点保留；通知页内提供跳转，不因打开通知页消除待办。
- 将现有轮询集中管理或复用，避免 Dashboard 与通知页同时重复查询同一计数。
- 不在发布时回扫所有历史申请生成站内通知，更不补发邮件。
- 以后若决定把邀请／申请变成真正的持久化通知事件，再单列事件清单、接收者、类别和去重规则；不借本轮隐式扩展个人通知。

### 10.6 发送页面与设置

- 系统入口放站点管理；团队入口放团队相关操作；项目普通公告和阶段完成入口明确区分。
- 编辑器提供格式按钮、名片选择器、收件人过滤／搜索、分页预览、邮件选项及正文预览。
- 普通公告提供草稿、定时、失效时间、确认发送和发送历史；发送后展示分发中／完成／部分跳过／失败汇总。
- 团队设置新增两个创建者专属开关，展示作用范围和“影响现有项目”的提示。
- 用户设置提供四类业务邮件偏好，注明不会阻断账号安全邮件。

## 11. 核心架构与模块契约

### 11.1 分层

```text
普通发送 API / 阶段确认 API / 既有业务入口 / 未来模块
                   │
                   ▼
    核心 NotificationService（权限、内容、收件、幂等）
                   │
       MongoDB 发布意图、名单分块、收件记录、投递记录
                   │
       可靠分发任务 + 周期恢复扫描（Celery）
             ┌─────┴─────┐
             ▼           ▼
        站内收件箱      邮件传输适配器
             │           │
        统一查询 API   SMTP / 现有安全邮件路径
             │
        前端通知中心
```

- SMTP 与 UI 不承担通知是否存在的事实来源；数据库中的发布意图和记录才是依据。
- 核心服务不导入任何具体 `app.modules.<name>`；模块可依赖核心服务，依赖方向单向。
- 不把核心发送器注册成可选模块；删除所有模块目录后，通知中心和邮件仍应正常运行。

### 11.2 内部调用契约草案

```python
NotificationService.publish(
    context=trusted_context,          # 服务端构造的操作者／受信服务上下文
    category="personal",
    source="module:<module_name>",
    event_type="<module_name>.<event>",
    audience=recipient_spec,
    title="...",
    body="...",
    body_format="bbcode_v1",
    related_resources=[...],
    requested_channels={"in_app", "email"},
    idempotency_key="stable-business-operation-key",
)
```

此为内部接口草案，不是允许浏览器传 `trusted_context` 或 `source` 冒充系统的 HTTP 接口。

- 模块执行于同一后端进程，是受信代码扩展，不宣称这一接口能沙箱隔离恶意模块。
- 注册来源和允许的类型／范围，服务器构造来源上下文；前端无法覆盖这些信息。
- 用户操作驱动的模块调用继承操作者权限；受信后台个人事件只能通知由模块业务验证过的相关用户。
- 系统／团队／项目分类不是模块可以任意用来绕过发送规则的标签；授权范围须由核心检验。
- 单次业务事件应提供稳定幂等键；模块重试不能重新制造不同事件 ID 绕过去重。
- 不接收可执行前端组件、任意 HTML 或任意外部跳转脚本作为持久化通知内容。

### 11.3 模块卸载与无订阅首版

- 保存安全的基础内容、来源标识和资源引用；核心可以不加载模块就渲染通知。
- 需要模块路由的按钮只通过通用贡献注册表解析；模块不在时隐藏／禁用，并提示功能不可用。
- 模块不存在或权限无法确认时，敏感资源回退为不可访问，而非默认放行。
- 不创建订阅集合、不增加订阅按钮、不默认给用户订阅团队或项目。
- 后续订阅模块自行决定事件产生与接收关系，再调用核心服务；核心偏好与投递能力可以复用。

## 12. 数据模型与索引草案

下列为逻辑职责，可在评审后细化字段名；优先使用新的核心集合，避免破坏旧 `message` 或现有成员集合。

### 12.1 Notification（发布意图与正文）

关键字段：

- ID、schema/body 格式版本、category、source、event_type。
- actor_user_id、作用范围（team_id／project_id）、安全的关联资源 ID。
- 标题、BBCode 正文；阶段记录包含受保护的 stage、target_id、confirmed_by、confirmed_at。
- 发布状态、创建／计划／发布／失效／撤回时间、内容版本。
- 收件规则、名单封存标记、准备游标／恢复检查点、汇总状态。
- 幂等作用域、幂等键哈希、请求内容指纹。

索引建议：幂等作用域 + 键唯一；状态 + 到期时间；范围 + 创建时间；操作者 + 创建时间。

### 12.2 NotificationAudienceChunk（收件快照分块）

- notification_id、chunk_no、收件用户 ID 列表、解析状态、完成标记。
- 单块拟定 100–200 人，不能把全站用户 ID 塞入一个可能触碰 MongoDB 16 MiB 上限的文档。
- `(notification_id, chunk_no)` 唯一；名单在公开分发前封存。完成分块可以重复处理而不会生成重复收件记录。
- 封存后不再按原筛选动态追加新成员；恢复只处理同一份确定名单。

### 12.3 NotificationReceipt（每人站内收件状态）

- notification_id、user_id、发布时间／稳定排序键。
- read_at、archived_at、必要的投递和可见性元数据。
- 不在每个收件人记录复制整篇正文，避免全站公告造成大量内容重复；但读取必须检查全局撤回／失效和接收资格。
- `(notification_id, user_id)` 唯一；用户 + 发布时间／ID、用户 + 已读／归档等索引依实际查询设计。

### 12.4 NotificationDelivery（邮件 outbox）

- notification_id、user_id、channel、状态、尝试次数、next_attempt_at。
- 租约 token／到期、稳定 Message-ID、最后错误类别、受理时间、人工重试记录。
- `(notification_id, user_id, channel)` 唯一；状态 + next_attempt_at、租约到期索引。
- 按 user_id 解析当前有效邮箱，不持久化全体 To／Cc 列表；确需审计邮箱时脱敏／限制访问。
- 安全邮件不把验证码内容复用到这一普通业务 outbox。

### 12.5 NotificationPreference（用户偏好）

- user_id 唯一；四类业务邮件允许值、版本、更新时间。
- 没有文档时使用明确默认值，不需要批量给旧用户写入新字段。
- 不增加“关闭验证码邮件”开关。

### 12.6 NotificationPolicy（范围策略）

- 拟使用独立的团队通知策略记录：team_id 唯一、两个管理员开关、version、修改者／时间。
- 缺省即关闭，不修改旧身份权限默认含义，不触发历史数据回填。
- 实施时如选择复用现有身份策略容器，必须证明不会与团队标签配置互相覆盖，且不绕过创建者校验；否则采用独立集合。
- 系统通知无需新增所有者配置；管理员管理权按 R01 使用现有 `ADMIN_EMAIL`，不新增身份模型。

### 12.7 审计与容量

- 发布、撤回、策略变更、重发记录使用现有审计能力或受限通知审计；不记录正文副本、验证码、密码和 SMTP 凭据。
- 首版未读数从可见收件记录计算，不先引入高风险的永久冗余计数器。性能不足时再通过测试引入可修复缓存。
- 权限检查批量加载成员／项目，不逐条通知触发 N+1 查询；计数不能通过全量加载正文得到。
- 分页、预览、收件解析和群发都有限制和游标，不能把全站名单放进一次 API 响应。

## 13. 可靠投递、并发与故障恢复

### 13.1 发布流程

1. 验证登录、范围权限、内容、目标、筛选规则及请求限流。
2. 用作用域内唯一幂等键持久化发布意图和请求指纹；相同键相同载荷返回原结果，不同载荷返回冲突。
3. 即时或到期后生成持久化名单分块；分块完成且封存前不公开部分名单的正文。
4. 将根事件置为可分发，投递 Celery 快速任务。RabbitMQ 不可用时，意图仍在数据库中待恢复。
5. worker 按分块幂等创建 Receipt 与 Delivery；唯一索引防止重复。
6. 分发检查点在对应写入后推进；崩溃重放不会丢失未处理分块。跨集合部分写入由恢复扫描补齐。
7. 邮件 worker 通过原子条件更新领取租约，检查权限、偏好、有效期后发送并记录结果。
8. 所有站内分块完成后更新发布汇总；邮件状态独立跟踪。

返回 `202` 表示“发布意图已可靠受理”，不是所有渠道成功。若连意图都无法保存，返回失败而不是假成功。

### 13.2 不依赖跨文档事务

- 实施前核对 MongoDB 部署，不能在未知或单节点环境直接依赖事务。
- 根意图、分块、收件、邮件不是一次原子写入；必须通过单文档 CAS、唯一键、检查点、封存标记和恢复扫描覆盖每个崩溃点。
- 不允许“先改完工作状态再直接 `.delay()` 且没有持久化补偿”的模式。
- 本首版阶段确认没有独立阶段状态变更，其声明与通知意图保存在同一根事件，避免制造新的双写业务状态。
- 既有安全邮件与校对稿接入时分别验证调用失败与重试语义，不要求它们通过未经验证的通用事务装饰器。

### 13.3 周期扫描与队列

- 必须有服务端周期任务扫描到期公告、未封存准备任务、待分发分块、到期重试与过期租约。
- 拟选 Celery Beat 单实例调度 + 幂等扫描任务；具体部署方式、CPU／内存和队列路由纳入部署审查。
- 扫描批次有上限，使用租约，重复扫描或两个任务竞争不能重复发布。
- 不用大量长时间 Celery ETA 消息作为唯一的定时持久层，不依赖页面访问触发恢复。
- 新增队列前确认已有 worker 会订阅；安全邮件优先级不能仅靠在没有消费者的队列里写一个路由名实现。
- 批量邮件建议低并发、可配置速率与退避；投递配额需依据 SMTP 服务限制测定。

### 13.4 exactly-once 的边界

- 可以保证业务事件、站内收件记录、逻辑邮件投递记录唯一。
- 不能在普通 SMTP 上保证“绝不重复且绝不丢失”的严格 exactly-once：服务端已接收后连接断开时，客户端可能不知道结果。
- 使用稳定 Message-ID、状态区分和保守处理降低重复风险；`unknown` 交给受控重试／人工判断，不能盲目当确定失败。
- 不通过删除旧记录再重建的方式“重试”，以免丢失审计与幂等性。

### 13.5 建议运行参数

这些是初值，不是未经测试的容量承诺：

| 参数 | 建议初值 |
| --- | --- |
| 收件列表页大小 | 默认 20，最大 100 |
| 预览页大小 | 默认 50，名单分页 |
| 名单／分发批次 | 100–200 人 |
| 前台未读轮询 | 60 秒，失败退避 |
| 恢复扫描周期 | 30–60 秒 |
| 发布限流 | 按操作者、范围、事件类型分别限制；安全邮件保留独立既有频率规则 |
| SMTP 并发／重试 | 按服务器与供应商限制配置；先低并发，瞬态错误指数退避，有上限 |
| 定时最大迟到窗口 | 1 小时，超限待处理，不盲目群发 |

## 14. API 草案

沿用项目既有认证、错误结构、分页／CORS 约定。以下路径和字段在实施 P0 固化，不视作现有已提供接口。

### 14.1 收件人与偏好

| 方法与路径 | 用途 |

| `PATCH /v1/me/notifications/<id>` | 仅修改本人的已读／归档状态，不能修改正文和接收者。 |
| `POST /v1/me/notifications/mark-read` | 按明确分类／截止位置批量已读，幂等。 |
| `GET/PUT /v1/me/notification-preferences` | 本人业务邮件分类偏好，支持版本检查。 |

### 14.2 普通发送与管理

| 方法与路径 | 用途 |
| --- | --- |
| `POST /v1/notifications/preview` | 受授权的内容与收件预览，不创建投递。 |
| `POST /v1/notifications` | 创建草稿、定时或即时普通公告，校验分类对应发送权限。 |
| `GET /v1/notifications/sent` | 仅可管理范围内的发送历史及汇总；不是全站所有通知搜索。 |
| `GET/PATCH /v1/notifications/<id>` | 发件管理详情；仅未发布内容可编辑且须版本校验。 |
| `POST /v1/notifications/<id>/publish` | 草稿明确发布，幂等。 |
| `POST /v1/notifications/<id>/revoke` | 撤回或取消计划，返回邮件不可撤回提示。 |
| `GET/PUT /v1/teams/<id>/notification-policy` | 策略读取和创建者专属更新；权限与团队通用修改区分。 |

### 14.3 阶段完成与名片

| 方法与路径 | 用途 |
| --- | --- |
| `GET /v1/projects/<id>/stage-notification-options` | 后端计算可确认阶段、目标语言及允许的收件筛选条件。 |
| `POST /v1/projects/<id>/stage-notifications/preview` | 受限阶段预览，不允许伪装为任意公告。 |
| `POST /v1/projects/<id>/stage-notifications` | 手动声明并发送，服务端生成受保护的事件类型和确认人。 |
| `GET /v1/projects/<id>/stage-notifications` | 有权限用户查看该项目交接声明记录；不返回其他成员邮件信息。 |
| `POST /v1/notification-project-cards/resolve` | 有限批量解析本人可访问项目；不可访问项目统一降级。可在实现时合并进详情渲染避免重复请求。 |

既有校对稿接口保持路径和关键行为不变，在内部接入通知服务。

### 14.4 草案请求示例

```json
{
  "category": "team",
  "scope": {"team_id": "..."},
  "title": "项目募集校对人员",
  "body_format": "bbcode_v1",
  "body": "[b]募集校对[/b]\n[project]...[/project]",
  "audience": {
    "mode": "condition",
    "base_roles": ["member"],
    "worker_qualifications": ["proofreader"]
  },
  "requested_channels": ["in_app"],
  "publish_at": null,
  "expires_at": null
}
```

- 幂等键通过请求头或项目既有等价机制传递，作用域包含操作者／来源，不能不同用户互相碰撞。
- 错误至少区分：未登录、无权限、非法对象／不可访问、空收件人、版本／幂等冲突、内容不合法、限流、暂时不可用。
- 资源不可访问的返回不得帮助枚举私有项目；详情响应不得携带之后才由前端隐藏的敏感原始字段。
- 预览只供确认，不成为永久发送授权；不直接接受前端渲染 HTML。

## 15. 兼容、初始化与迁移边界

### 15.1 既有迁移冻结约定

遵守 `docs/README.md`：不修改迁移运行器、不重写已应用版本、不默认新增 `0009` 或重跑 `0008`。

拟采用新集合 + 缺省策略／偏好，尽量无历史文档改写。但**新集合及索引的创建仍是需要评审的数据库变更**，不能把它伪装为“完全无需数据库操作”。

- P0 固化新集合、索引、唯一约束及容量估计。
- 使用项目现有可验证的索引初始化惯例；提前检查索引冲突和空集合初始化，不擅自写一个替代迁移运行器。
- 需要历史数据搬迁、已有集合新增强制字段、唯一索引清理或站点所有者回填时，先提交专项方案并获批。
- 禁止为兼容新功能删除旧集合、旧索引或业务记录。

### 15.2 旧 Message 数据

- 先统计是否实际存在记录及是否被旧接口消费，只读盘点，不将内容输出到公开日志。
- 首版默认不迁移、不补发、不删除；若有必须保留在新 UI 中的历史记录，另设计只读兼容或迁移审查。
- 不根据模型存在就断言生产库为空。

### 15.3 旧邮件任务与接口

- 新旧发布短暂共存时，旧队列中的 `tasks.email_task` 名称、参数和模板仍可消费。
- 旧业务入口接入后只有一个主投递路径，不能同时调用旧 `send_email` 与新 outbox 导致双发。
- 没有部署新版消费者前，不投递新版专属任务到生产队列。
- 回滚时先停新发布／调度，处理或保留新任务，不能让旧 worker 静默丢弃未知任务。

### 15.4 上线边界

- 不回填旧项目的阶段完成状态，不自动通知旧邀请／申请，不向历史用户补发校对稿。
- 新功能首启默认管理员开关关闭，普通群发邮件默认未勾选。
- 通知核心的发布总开关可用于发布／运维停发，不是可选模块开关；停发普通通知不能停用密码重置邮件。
- 开发环境邮件必须限于批准的测试收件人或测试 SMTP，不得沿用真实全站收件列表做验收。

- 备份数据库／配置并验证恢复方法，记录当前 release、镜像与新集合初始化清单。

### 19.2 发布步骤草案

1. 先以普通通知发布关闭、开发邮件受保护状态部署兼容后端与消费者。
2. 验证新集合索引、旧邮件任务、通知 API 和权限拒绝行为。
3. 启动经批准的扫描调度，确认任务队列有实际消费者、无重复调度造成的异常。
4. 部署匹配前端，验证旧功能与移动导航。
5. 使用专门的测试账户／团队／项目开启通知并做小规模端到端验证。
6. 检查测试邮箱、站内数量、失败／跳过汇总及权限变更后的历史可见性。
7. 执行现有开发环境 Verify 流程，并人工验证新功能；自动健康检查不能代替通知业务验收。
8. 向用户提供开发地址、release、截图、已知限制，等待效果审查；不部署生产。

### 19.3 观测指标

- 发布受理量、拒绝／限流量、收件解析耗时、积压意图数。
- 待分发分块、待投递／重试／未知状态邮件数、最老等待时间。
- SMTP 受理率／错误类别、因偏好／邮箱／权限跳过数量。
- 恢复扫描执行时间、租约回收次数、队列消费心跳。
- 未读查询与列表延迟、数据库查询次数、内存和批量操作峰值。
- 仅记录必要 ID、计数和错误类别；不把正文、验证码和完整邮件地址写入一般日志。

### 19.4 回滚顺序

1. 先停普通通知新发布与定时扫描，保留站点安全邮件原有能力。
2. 决定正在处理的新任务是由兼容 worker 排空，还是暂停并保留；不能让旧 worker 消费不认识的任务。
3. 切回已保存的前后端 release 和部署配置，确认旧 API、登录、密码重置、项目操作可用。
4. 保留新增通知集合和投递记录，不删除新数据来“恢复旧版本”。后续重新启用前核对未完成任务，避免重复邮件。
5. 已被 SMTP 接受的邮件不能通过回滚收回；将实际投递情况列入回滚记录。
6. 发布修复后先对照旧幂等键、Message-ID 和投递状态做恢复验证，再开启普通群发。
